## 1. 调研深度跃迁规则（Gate Transition Rules）

调研按证据深度逐级跃迁，绝不无证据跳级，也绝无必要所有项目盲目全读到底：

```
[L1: 身份与合规探测] 
    │
    ├── (无 License / 停更 > 2年 / 纯同名无关项 / 纯 PPT-Demo) ──> [停留在 L1: 标记暂存/淘汰]
    │
    └── (License 合规 + 活跃 + 命中业务痛点) ──> [L2: 机制与工作流下钻]
                                                    │
                                                    ├── (纯教程/方法论/CLI工具，无代码侵入) ──> [形成 L2 调研卡: 借鉴原则/暂存]
                                                    │
                                                    └── (涉及写文件/调模型/常驻进程/候选底座) ──> [L3: 源码与安全审计]
                                                                                                    │
                                                                                                    ├── (安全隐患/强制出机) ──> [形成 L3 调研卡: 标记红线淘汰]
                                                                                                    │
                                                                                                    └── (架构优异 + 试用高价值) ──> [L4: 隔离试用提案 (需用户显式授权)]
```

- **L1 停放条件**：无 License、年久失修（>2年）、纯占位符/空壳，立即终止深入并记录原因。
- **L1 → L2 晋级条件**：协议合规（MIT/Apache/BSD 等；GPL 需单列传染风险），官方自述功能击中已知业务痛点。
- **L2 → L3 晋级条件（强制安全门）**：只要具备以下特征之一，强制下钻到源码层核查：
  1. 具有本地文件修改/写入能力（如 Vault 插件、自动代码生成、文件覆盖）；
  2. 会调用外部 LLM API（必须查明 Prompt 注入内容、API 转发端点、有无硬编码 key 或数据外泄）；
  3. 涉及常驻后台、守护进程、端口监听或网络通信；
  4. 被提名为科研台/学习台/工作台的“架构底座候选”。
- **L3 → L4 跃迁条件**：**严禁 AI 擅自启动 L4 实测**。必须提交完整的沙箱隔离方案、测试用例与回滚方案，经用户明确批准后方可执行。

## 2. 源码级审查核验清单（Checklist）

### 2.1 依赖与架构剥离
- [ ] 最小运行环境要求（Node.js / Python 版本 / Docker / 硬件 GPU 要求）；
- [ ] 项目核心目录骨架与关键入口文件定位；
- [ ] 重型框架依赖核查（是否依赖 LangChain、LlamaIndex、AutoGPT 等，还是纯原生轻量实现）。

### 2.2 数据流与网络通信审计（安全红线）
- [ ] 检索所有网络通信点（`fetch`、`axios`、`requests`、`httpx`、WebSocket 等）；
- [ ] 确认通信端点：纯本地（`127.0.0.1` / `localhost`）还是外部云端；检查是否有隐蔽 Telemetry 埋点；
- [ ] 检查 LLM 调用：是直连官方提供商，还是强制走开发者自建代理？是否允许自定义 `BASE_URL`（支持本地 Ollama/vLLM）；
- [ ] 检查文件写域：写操作是否被限定在用户沙箱/指定目录，是否存在覆盖宿主环境或工作区正本的风险。

### 2.3 源码除魅与“纸老虎”检验（Anti-Hype）
- [ ] **自研逻辑 vs Prompt 兜底**：核心流程是算法/规则状态机，还是仅靠向闭源大模型塞大段 Prompt 兜底？
- [ ] **“自主性”真实度**：宣称的“Autonomous Multi-Agent”是否存在真实的回滚、容错、分支合并机制，还是遇错即崩的 Demo 玩具？
- [ ] **示例水分**：README 的运行示例是真实动态生成的，还是硬编码的静态假数据（Mock）？

## 3. 业务场景靶向映射（5 大业务现场）

调研必须回答具体对接哪一个业务现场，杜绝“对科研很有用”等泛化空话：

1. **科研台 (Research Desk)**：四论文 Ownership 证据链、鲁组并发分析（Petri网/MHP/死锁）文献追踪、论文蓝图与引文防幻觉。
2. **学习台 (Learning Desk)**：三档掌握要求（最低/正常/长期）、错题归因与闭卷复测、尝试/反馈/再尝试流转、材料原段回跳。
3. **工作台 (Workbench)**：任务依赖 DAG、门禁与审计（AC-01~AC-10）、多 Agent 会话与 Worktree 隔离、不可抵赖回执。
4. **考研与基础学术训练 (Exam Prep)**：数三/英一/408 的“真工作流”（AI+OCR 结构化转录、错题与盲区索引，拒绝无工作流的静态笔记堆积）。
5. **底层工程与工具库 (Infra & Skills)**：单机大模型轻量推理、格式转换、作为独立的 Claude Code Skill 调用。

## 5. 多 Agent 并行调度纪律（5 Caps 协议）

为了确保多 Agent 并行产出的质量一致性与防幻觉，所有子代理均受 **5 Caps 协议** 硬约束：
1. **URL Cap**：仅限指定的官方 GitHub 仓库及相关文档，不漫游第三方二手网页。
2. **Tool Cap**：只读工具审查，严禁执行 `install`、`clone` 或运行未知代码。
3. **Word Cap**：报告正文控制在 800–1200 汉字以内，结论先行，杜绝无意义注水。
4. **Time Cap**：单项目调研时长有上限（常规 ≤12 分钟）。
5. **Done-When 判据**：必须齐备 6 维指标（画像、机制、除魅/安全、业务槽位、局限反例、处置建议），查不到的事实必须如实写“官方未公开/未发现”，严禁留空或臆测。
