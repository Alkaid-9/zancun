## 1. 问题

多线程程序的 UAF(Use-After-Free)静态检测。值流分析类方法(Saber、Pinpoint、Canary)精度和效率好,但**没有充分考虑并发原语与复杂控制结构引起的因果约束**,导致假阳性/漏报:

- **Canary 的具体失效场景(§III 动机案例)**:主线程持锁 ι 时 fork 子线程(fork 在 lock/unlock 之间),子线程内 free。Canary 只建模"偏序约束"(线程内顺序、fork/join)和"一致性约束"(值流过程中内存不被并发改写),**识别不了 lock/fork 耦合因果**——子线程的 free(l26) 必须等主线程释放 ι 之后才能执行,故 l9(主线程持锁期间的 use)先于 l26,第一种交错下无 UAF;Canary 会误报;
- **循环结构**:静态值流图缺运行时信息,现有方法(CBMC)固定展开次数,精度-效率难平衡。

真实动机:CVE-2021-21148(Chrome 渲染引擎 UAF,远程代码执行)。

## 2. 方法(四阶段框架)

### 2.1 中间代码(§IV-A)

源码转 LLVM 风格中间码,12 种语句:malloc/use/free/read/write(内存),acq/rel(锁),fork/join(线程),label/branch/branch(cond)(控制流)。这是把"程序"规约成 PN 可建模事件流的第一步。

### 2.2 三类约束(定义 2–4,本文的概念骨架)

对执行语句序列 $\Gamma = (l_i \mid i \in \mathbb{N}^+)$:

1. **控制流因果约束(定义 2)**,三型:
   - 线程内:同线程 $l_j, l_k$,$j < k$;
   - 线程间 fork/join:fork 先于子线程所有语句;子线程所有语句先于 join;
   - **lock/fork 耦合因果**:若 $l_i, l_k$ 是锁请求/释放、$i < j < k$、$l_j$ 是 fork,则持锁区间内语句 $l_y (y \in (j,k))$ 与被启动线程中(需要该锁的)语句 $l_z$ 之间存在耦合因果——这是对 Canary 约束系统的**增量贡献点**;
2. **UAF 触发约束(定义 3)**,两型:读/写因果(读要读到特定写,其他写必须在该写之前);**free 先于 use** 即触发 UAF;
3. **条件满足约束(定义 4)**:依赖条件的合取 $\theta_1 \wedge \theta_2 \wedge \cdots \wedge \theta_j$(值流边上的路径条件)。

检测原理 = **三类约束的兼容性分析**:若"UAF 触发所要求的执行序"与"控制流因果允许的执行序"不兼容,则该源汇路径无 UAF。

### 2.3 分段 Petri 网(定义 5,PN 建模选择)

$$\Sigma = (P, T, F, S, M_0, \lambda)$$

对经典 PN 加**段集 $S$** 和**段映射 $\lambda: (P \cup T) \to S$**;Table 3 给出 12 种中间码语句的建网规则。锁建模为库所;为刻画 lock/fork 耦合,设计两个**伴随标签**:
- $\alpha(m, \iota, u)$:线程 m 在 u 持有 ι 时请求 ι;
- $\beta(m, \iota, u)$:线程 m 持 ι 期间启动 u、随后释放 ι;
二者之间的 lock/fork 耦合因果在网上用点线表示。

**与 02 篇(PNULock)的关键区别**:输入是**源代码(静态)而非运行轨迹(动态)**,所以网里保留了 branch/loop 结构(PNULock 的轨迹网恰恰为了简化而扔掉了决策结构);段(segment)概念从组内前作(锁增广分段图,《软件学报》2021,本文引文 [30])继承。

### 2.4 静态分段值流图(定义 6)+ 源汇路径(算法 4)

$$\wp = (O, \hat{V}, R, C, S, \sigma)$$

在经典静态值流图 $G = (V, O, R, C, \sigma)$(变量节点、内存对象节点、数据依赖 + 干扰依赖、依赖条件)基础上,变量节点扩展为 $\hat{V} = \{n_i = (v_j, s_z, l_k)\}$ ——**带段号**,段号取自分段 PN(算法 3 完成关联)。算法 4 从 free 节点出发,找同一内存对象上可达的 use 节点,构造源汇路径 $\rho$ 并顺带算出 UAF 触发与条件约束。

### 2.5 分段 PN 展开 + 循环处理(§V-B/C,本文的技术亮点)

- 展开成 occurrence net 判定变迁间**并发/冲突**关系(控制流因果约束的判定引擎;cut-off 事件 = 局部配置重复出现的起点,红框标记);
- **循环结构**:cut-off 事件描述"与之前相同的状态"(循环第一轮 ≈ 第二轮),于是**取 cut-off 事件与其源事件之间的全部事件构造"伴随 cut-off 事件的 PN 展开段"**,该段即循环体,替代 CBMC 固定次数展开——用展开的语义等价性做循环摘要,这是把 PN 理论工具反哺程序分析的巧点。

### 2.6 兼容性判定(算法 5)

对每条源汇路径:先查条件约束可满足;再对 UAF 触发约束中的每个序 $n_i < n_j$ 找对应变迁 $t_1, t_2$,依次判:同一展开段(循环内)→ 兼容;lock/fork 耦合 → 按耦合方向判;并发 → 无序约束、继续;非并发 → 按展开偏序判;兜底按行号判。**不兼容 ⟹ 报告 UAF**(加入 $\hat{\Lambda}$)。兼容性提前剪枝也是时间开销低于 Canary/Saber 的原因。

## 3. 实验

- 环境:i9-13900HX,60GB 内存,Ubuntu;
- 数据集:**Juliet Test Suite**(C/C++ UAF,393 个漏洞〔[刊内 p.178002/PDF p.9],08-24 R1-f 补锚〕)+ 5 个自建多线程程序;
- 对比 **Canary**(PLDI'21,源汇可达 + SMT)与 **Saber**(ISSTA'12,稀疏值流):
  - vs Canary:**recall +25%、precision +33.3%**〔[刊内 p.178003/PDF p.10],08-24 R1-f 补锚;摘要同口径 [PDF p.1]〕。Canary 漏检"free 与 use 同线程"的场景(CEW416-1、Test1/2/5),在 lock/fork 耦合场景误报(CEW416-5、Test4);
  - vs Saber:**recall +3%、precision +15.1%**(Saber 只看源汇可达,不识别任何并发因果);
  - 时间:比 Canary 少 12.6 ms、比 Saber 少 21.3 ms(论文表述为"time complexity"实为平均耗时)。

## 4. 局限(论文自认 + 我的补充)

论文自认:
- while/do-while/switch 结构精度不足,声明未来做**动静结合**;
- 未来才扩展到死锁/数据竞争/内存泄漏检测与自动修复。

我的补充:
- **评测规模是本文最薄弱环节**:Juliet 是合成微基准,5 个自建程序无公开;Canary 原文在数百万行真实代码(如 Linux 驱动)上评测,本文没有任何真实项目数据,"+25% recall"的外推性存疑;
- "time complexity reduced by 12.6 ms"的表述在方法论上不严谨(毫秒是耗时不是复杂度),且未报告展开的最坏情况开销——分段 PN 静态建模保留了分支,状态爆炸风险比 PNULock 更高,但论文未讨论;
- 指针分析精度(alias analysis)如何获得没有展开说明,而这恰是静态 UAF 检测的传统瓶颈;
- 与 Canary 的对比公平性:Canary 面向全类 inter-thread value-flow bug,本文只测 UAF 子集。

## 5. 进组视角

**复现/扩展切入点**

- 扩展 A:补真实项目评测(如 SV-COMP 并发子集或 CVE 复现集),这是最能给这条线补短板、也最容易做出增量的工作;
- 扩展 B:把伴随 cut-off 展开段的循环摘要单独抽出来,与 CBMC 定次展开做对照实验——这个点目前埋在正文里,值得独立量化。

**与 T 课题的关系(T3 直接借力)**
- T3(use-after-poison 值流检测)的映射:**free → "记忆条目被投毒";use → "agent 消费该记忆生成动作";值流图 → agent 间信息流图(消息/共享记忆/工具返回值);lock/fork 耦合因果 → agent 会话/工具调用的时序耦合**。检测框架同构:投毒源→使用汇的路径 + 三类约束兼容性;
- W1-C 已核实的辩护话术:同题(源汇可达 + 并发因果)Canary 用纯 SMT 编码,本组用 PN 承载因果约束——**载体差异 = 可解释的偏序证据 + 天然对接展开重演**,这套话术对 T3 直接可用;
- 与 T1 的接口:T3 检出的 use-after-poison 路径,可交给 T1 的展开机器生成确定性重演调度(02 篇阶段二),形成"静态检出 + 动态确认"闭环——组内 UAF(静态)与 PNULock(动态)尚未合并,这个闭环本身可能就是一篇论文。
