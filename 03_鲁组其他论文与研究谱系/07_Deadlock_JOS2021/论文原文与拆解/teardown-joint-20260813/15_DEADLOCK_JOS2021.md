# 15 · 锁增广分段图:基于锁增广分段图的多线程程序死锁检测（D2线）

## 1. 问题

动态死锁检测方法从运行轨迹挖掘锁图/分段图，但现有模型存在三类关键信息丢失，导致多种死锁误报：

1. **循环中同一锁语句多轮执行无法区分**[p.2-3, L93-94]：位于循环中的同一 acq 语句，某轮可能死锁、某轮不会，但锁图/锁树/扩展锁图都无法区分。Program 1 例：threadA 第1轮循环因持有门锁 G 不会死锁，第2轮才会死锁，分段图和扩展锁图把两轮都报成死锁 [p.3-4, L138-147]。

2. **锁释放-获取导致的跨线程因果被忽视**[p.2, L87]：分段图仅刻画 start/join 因果，但 threadA 释放锁 G 与 threadB 获取 G 也构成因果依赖，无法被传统分段图建模。Program 1 例：threadA 第1轮持 G 期间启动 threadB，G 的释放与 threadB 后续操作形成"锁-start"耦合因果，使两个嵌套获取不能并发，但分段图中段间无路径 [p.3, L277-280]。

3. **曾经持有而已释放的锁导致的假阳性**[p.3, L285-297]：传统锁图只记当前持有锁集，丢失历史持有锁。threadB 获取 p 前必先获取并释放 n，threadC 获取 q 前必先获取并释放 m；两者当前持有锁集互不相交，看似可并发，但历史持有的 n/m 形成门锁导致互斥。已有方法包括 ConLock+ [21] 虽曾指出此问题但需靠重演排除，检测阶段无法消除 [p.3, L121-123]。

根因：现有模型折叠了执行实例、丢失了释放-获取因果、忽视了历史信息。

## 2. 方法（两个增广模型+一套判定规则）

### 2.1 五关系因果体系（定义1）[p.5-6, L318-340]

五类依赖/互斥关系为后续建模的词汇表：

1. **线程内因果** $e_i <_{thread} e_j$：同线程且先后执行
2. **线程启动因果** $e_k <_{start} e_m$：start 操作建立的因果（start 之前的事件先于子线程事件）
3. **线程 join 因果** $e_k <_{join} e_m$：join 操作建立的因果（子线程终止后，父线程才继续）
4. **"锁-start"耦合因果** $e_k <_{lock\_start} e$：线程 u 持锁 o 的区间内执行 start(u,v)，则 u 该区间内的事件先于 v 中需要 o 的事件 [p.5, L323-325]
5. **"历史持有锁-持有锁"耦合因果** $e_i' <_{lock\_held} e_j'$：线程 u 获取历史持有锁 o 必先于线程 v 最后一次获取持有锁 o；即若 Lock_Intersection = lockSet_OnceHeld(e_i) ∩ lockSet(e_j) ≠ ∅，则对每个 o ∈ Lock_Intersection，u 获取历史 o 的操作先于 v 最后一次获取持有 o 的操作 [p.5-6, L330-335]

还包括：
- **锁集互斥** $e_i \#_{lockSet} e_j$：当前持有锁集相交 [p.5, L327-329]
- **历史持有锁集** lockSet_OnceHeld(e_i)：线程获取当前各持有锁过程中曾获取过的锁集 [p.6, L331-332]

### 2.2 锁增广分段图（定义3）[p.6-7, L433-472]

在传统分段图基础上的两大增广：

**增广点(1)：锁释放为分段点** [p.6-7, L441-447]
- 规则(d)：当线程 u 在段 s 执行 rel(u,l) 操作时，若 u 此前获取 l 不在段 s 中，则添加新段
- 规则(e)：当线程 v 在段 s' 执行 acq(v,l) 时，反向找首个获取 l 的段 s''（属他线程且未释放 l），则：
  - 从 acq(v,l) 处开始新段 s'_new
  - 在 s'' 的后代中找首个以 rel(u,l) 结尾的段 s''_desc
  - 在 s''_desc 与 s'_new 间添加有向弧，物化"锁-start"耦合因果

**增广点(2)：φ_s 标签记录段内锁事件序列** [p.6-7, L464-472]
- φ_s(segment) := 段内各锁操作序列，带轨迹序号 ID；带下划线表示释放，无下划线表示获取
- 例：段4 标签 = (n(32), m(33), m(34), p(35), q(36), q(37), p(38), n(39)) [p.6, L407-409]
- 历史持有锁集 lockSet_OnceHeld 由标签串反向扫描计算 [p.6, L557-564]

形式化：SegG_Lock_σ = (SegSet_σ, SegR_σ, φ_s, φ_r)，生成规则详见 Def 3 六条 [p.6-7]。

### 2.3 时序增广锁图（定义4）[p.7, L514-527]

在扩展锁图基础上添加执行次序信息，区分循环中多轮执行：

弧标签从 ⟨seg1ID, (threadID, lockSet), seg2ID⟩ 扩充为 ⟨seg1ID, (t, lockSet), **m**, seg2ID⟩(k)，其中：
- **m**：线程 t 第几次获取 lock2（区分同语句不同轮次）
- **k**：轨迹序号 ID（定位操作在分段图中的位置）

例：图3中弧2原为 ⟨5,(threadA,{G,o1}),5⟩，增广后为 ⟨5,(threadA,{G,o1}),1,5⟩(5)，1表示第1次获取 [p.7, L483-486]。

### 2.4 "历史持有锁-持有锁"耦合因果关系图（定义5）[p.7, L571-588]

对每个候选环路 c，构造局部判定图 DependG_Lock_c = (V_c, R_c)：

**顶点生成规则** [p.7, L575-581]：
- 对环路中各对锁操作 e_ki = acq(u,o), e_kj = acq(v,o)，若 o ∈ lockSet_OnceHeld(e_ki) ∩ lockSet(e_kj)：
  - 添加顶点 (v,o(y))：v 最后一次获取持有锁 o 的操作
  - 添加顶点 (u,o(x))：u 获取历史锁 o 的各操作（可能多个）
  - 添加有向边 (u,o(x)) → (v,o(y))：历史持有-持有因果

**边生成规则** [p.7-8, L583-584]：
- 对 V_c 中任意两顶点 (u,p(i)) 与 (v,q(j))，若 u=v ∧ i<j，则添加边 (u,p(i)) → (v,q(j))：线程内因果

**判定**：若 DependG_Lock_c 存在有向环，则环路 c 对应的潜在死锁是误报 [p.8, L586-589]。

Program 1 例 [p.8, L590-598]：环路{11,15}对应的 DependG_Lock_c 中，(threadB,n(22)) → (threadC,n(32)) → (threadC,m(33)) → (threadB,m(21)) → (threadB,n(22))，形成环，说明因果无法同时满足，故非真实死锁。

### 2.5 检测算法（五条规则）[p.8, L622-628]

```
对每条时序增广锁图中的有向环路 c，判定为潜在死锁的充要条件：
1. c 在时序增广锁图中构成有向环；
2. 环路中锁申请操作分属不同线程；
3. 环路中任意两操作在锁增广分段图中无路径相连（无线程间因果与lock-start耦合）；
4. 环路中任意两操作持有锁集互不相交；
5. 环路对应的"历史持有锁-持有锁"耦合因果关系图不存在有向环。
```

算法1完整伪代码 [p.8-9, L630-672]：FOR EACH 环路，依次检查规则1-5，全过则加入死锁集。

复杂度：未明确分析，但基于图矩阵方法求环（多项式，[28] Yuan 1992），相对 iGoodlock 的图遍历（指数）更优 [p.8, L833-835]。

## 3. 实验

**原型系统** [p.8-9, L736-746]：基于 CalFuzzer 开发三层架构
- 输入层：Java 多线程程序
- 处理层：轨迹挖掘、两图构造、算法1检测
- 界面层：可视化两图与死锁结果

**基准与对比** [p.9, L789-797]：
- 14个程序（8 个 CalFuzzer 例程 + pingpong/cyclicDemo + ConLockDemo + PetriDeadLockDemo + OnceHeldLockDemo + MulThreadDeadlockDemo）
- 对标 iGoodlock（CalFuzzer 内置，基于循环锁依赖链 + DeadlockFuzzer 随机重演）

**核心结果** [p.9, Table 4]：

| 程序 | 潜在死锁数 |  误报数  | 时间(s) | 内存(MB) |
|------|----------|--------|--------|---------|
|      | iGood/本 | iGood/本| iGood/本| iGood/本|
|Test1a| 1/1      | 0/0    | 0.198/0.157 | 3.695/5.219 |
|ConLockDemo| 4/3  | 1/0    | 0.192/0.176 | 3.884/4.730 |
|PetriDeadLockDemo| 2/1 | 1/0 | 0.135/0.112 | 3.898/4.812 |
|OnceHeldLockDemo| 4/2 | 2/0 | 2.158/2.118 | 3.904/4.956 |
|MulThreadDeadlockDemo| 2/1 | 1/0 | 0.726/0.235 | 3.816/5.026 |

关键发现 [p.9, L831-841]：
- **精度**：本方法零误报（对比目标类型样例），消除了传统方法无法处理的 lock-start 耦合与历史持有锁误报
- **时间**：有潜在死锁时优于 iGoodlock（图矩阵多项式 vs 图遍历指数）；无死锁时略差（需构造两张增广图与因果图）
- **内存**：高于 iGoodlock（两图 + 标签与因果图信息代价）

## 4. 局限（论文自认+补充）

**论文自认** [p.9, L852-857]：
- 仅考虑五原语 start/stop/join/acq/rel，wait/notify/notifyAll 等通信原语未覆盖
- 条件控制结构（if/else）对死锁影响未考虑
- 单条轨迹捕获行为有限
- 程序自动修复方向未探索

**补充局限**：
- **规模与渐近性**：14个程序均为教学级，最大多线程 OnceHeldLockDemo 时间跳 10 倍级（2.158s vs 0.726s），表明历史锁计算自身有规模风险，但负载未达到展开/矩阵算法的真正瓶颈 [p.9, Table 4]
- **跨运行映射假设**：线程 fork 序、锁申请序两次运行一致的假设在数据依赖调度程序上破裂，失败模式未讨论 [p.9]
- **单轨迹假阴性**：动态法固有漏报，尤其对未观测轮次/分支的死锁无法报告
- **重入/条件等待未处理**：synchronized 重入、tryLock、wait 等实际 Java 原语抽象成单令牌互斥，可能产生伪死标记

## 5. 进组视角

### 5.1 与D2谱系的关系（2021 JOS vs 2026 TST SegLock）

**核心发现**：本篇 2021 JOS 是 SegLock (04) 的直系方法学前身。

**继承关系**：
- **定义3锁增广分段图**与**定义4时序增广锁图**的两增广点（锁释放分段+φ_s 标签+m/k 轮次序号）在 SegLock 04 篇中原样继承为 Def 3 与 Def 4
- **Def 1 五关系体系**（lock_start + lock_held 耦合因果）在 04 篇升级为同样的五关系 + 历史锁耦合因果图 Def 5 判环 [SEGLOCK.txt L735-750]
- **程序实例与案例**：Program 1 及其三条轨迹 σ1/σ2/σ3 直接复用在 SegLock 论文，标记信息与段结构一脉相承 [SEGLOCK.txt L892-975]

**差异与升级**（04相对本篇）：
1. **模型替换**：从 PN 思想（伴随变迁+配置展开）退回到**纯图近似**——时序增广锁图的弧标签能做 m/k 实例区分而无需 1-safe 网；历史锁因果图判环替代了 PNULock 的配置枚举 [04卡 §2-2.4]
2. **效率代价**：04 声称检测时间降至 1/2–1/6（相对 PNULock）[SEGLOCK.txt L1165-1180]，本篇与 iGoodlock 时间接近（相差不超过倍数），体现了轻量化的收益
3. **覆盖面**：两篇都未做 PN 展开 vs 图方法的能力对照，本篇的五规则判定是否遗漏 PN 展开能检出的某类交错？[未见论证]
4. **重演**：本篇结论 [p.9, L714-734] 明确指出 ConLock+ 需重演才能排除历史锁误报，但本篇检测阶段即消除；04 篇则跨越到两阶段重演的 DLAE 分层+SchdG 拓扑排序，实现确定性一次成功 [04卡 §2.5, §5]

**谱系判断**：本篇是"方法学原型"，04 是"工程优化迭代"——同一套因果体系在本篇以五原语+五规则落地，04 篇则沿袭同一词汇表但换载体（展开→增广图）并补完重演闭环。作者阵容对应：郑佳静在本篇二作（硕士生身份），04 篇已去中科曙光；王小宇本篇参与本科阶段 [p.9, L970-971]，04 篇升为核心二作 [SEGLOCK.txt 2026年论文] ——人员演进反映课题线发展的连续性。

### 5.2 复现与扩展路径

**复现入口**：
- 第一步：Program 1 手工构造表2轨迹，逐条应用 Def 3/4 构造两图，验证五规则对四个环路的判定（图1/2/3/4 一一核对）
- 第二步：用 CalFuzzer 采 4 个基准程序轨迹，手工/脚本构两图，对照 Table 4 验证精度与时间
- 成本：相对 PNULock 手工展开复现更低（图构造 vs 网构造+前缀生成）；对标 SegLock 04 复现的入门难度

**扩展方向**：
1. **与 PNULock 的能力对照**[重要]：构造一个 J 类（join-锁混合等待）例子，两条管线实测能否都报；若 PNULock 报而本篇漏，则说明展开路线有超越图方法的检出能力——这对组内"重 vs 轻"路线抉择有直接价值 [与 02b 卡特命命题甲同调]
2. **历史锁计算复杂度精确化**：OnceHeldLockDemo 上三方法时间同时跳 10 倍级，表明历史持有锁集反扫及因果图判环自身的非平凡代价；精确分析该环节复杂度、给出形式化界 [本篇未提供]
3. **跨运行映射失败模式**：数据依赖的 fork 序/锁申请序破裂时，重演如何兜底？是否需要语义等价类映射而非字面相同？
4. **wait/notify 扩展**：模型是否天然容纳 wait 系原语，还是需要新增因果类型？与 PNULock 自认的通信死锁 PSPACE-complete 成本如何权衡？

### 5.3 对 T1/T3 课题的迁移映射

**T1（MAS 传播割集+确定性重演）**：
- 五关系词汇表的类比：acq/rel → agent 对共享资源的占用/释放，lockSet → agent 当前权限集，lockSet_OnceHeld → agent 历史权限/上下文
- DependG_Lock 的图判环与 MAS 权限升级链检测同构：把"历史持有-持有锁"替换为"权限持有-权限申请"，能否框架化为"权限依赖图"？
- 确定性调度器的迁移：本篇缺少 PNULock 的"配置张成子网直接读授权序列"设计，但五规则的分解方式可作为 MAS 场景中重演触发策略的参考

**T3（use-after-poison 与分段 PN）**：
- 本篇 Def 3 的"锁释放分段点"与静态侧 STCFG 的 lock/unlock 作分段点思路平行 [见 08 卡 §4.1] ；两边的"细化因果"方向一致
- φ_s 标签串的因果历史记录与值流分析中的"源汇路径追踪"互补；能否整合为"权限+值"的二维图方法？
