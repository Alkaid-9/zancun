## 0. 为什么要重开这个问题

用户原话："我感觉是我们一直架构不清晰"。这不是模糊的抱怨，磁盘上有三条具体证据：

1. **`WORKBENCH.md` 自己的表述在两个角色之间摇摆**——09-10 设计里工作台与学习台/科研台平级；09-10 晚用户校正"合并入口不删去这些职责"（要求即使合并首页也保留独立验收职责）；09-14 又把工作台正式降级为共享服务层。三次表述都对，但从未有一份文档把"工作台到底是不是一个独立的台"当第一原则明确回答，只是每次冲突出现就打一个补丁。
2. **两份参考清单（`REFERENCE_NOTES_20260915.md` 13项 + `BRIDGE_TOOL_REFERENCE_CATALOG_20260831.md` 24仓）把两类性质不同的工具混在同一个"要不要引入"的筐里问**：PlanWeave/ai-project-os/Remit 解决的是"任务怎么被执行、验收、追责"；NotEMD/LearnGraph/ThoughtDAG 解决的是"知识/材料怎么被组织、关联、追溯"。这是两个维度，选型标准完全不同，但从未被分开讨论。
3. **"科研驾驶舱"事件本身可能就是这个模糊的直接产物**——见 §4，R11 截图最有参考价值的部分（"一项目入口＋证据脊柱＋阶段门＋下一步"）本质是任务/阶段结构，而它被当成了第三个独立产品来做，这恰好复现了工作台身份不清的老问题。

## 1. 提出的第一原则：object 与 view 分离

09-10 校正里已经有这句话："同一 object 多 view"、"两份评价引用同一产物，允许只填写一边"。这条原则当时只是修正了"学习科研不强制二选一"这一个具体分歧，从未被提升为组织三个台的**顶层设计原则**。本提案把它提升为顶层原则：

- **object（材料/对象）**：一篇论文、一个概念、一个来源、一次实验、一道练习——独立于任何台存在，有自己的身份。
- **view（评价/视角）**：不同的台，是同一批 object 上叠加的不同评价维度，不是三个平行的容器。

## 2. 三个台的重新定义（提案）

| 台 | 回答什么问题 | 评价对象是什么 | 成功标准 |
|---|---|---|---|
| **学习台** | 我掌握了吗？我的证据是什么？ | 用户自己对某个 object 的尝试、反馈、复测 | 独立作答/复测/迁移证据，不是"读过"或"AI 讲过" |
| **科研台** | 关于这个 object，世界/文献里已知什么？我的判断怎么变化的？ | object 的主张、方法、来源、谱系、与其他 object 的关系（对应已设计未实现的八观察面：问题/方法/主张/谱系/团队/实现/操作/轨迹） | 来源可追溯、判断变化有据可查，不要求用户本人已能复现 |
| **工作台** | 这件事谁负责、排到第几、验收状态是什么？ | **不是同一种 object**——是任务/行动项：owner、优先级、依赖、预算、验收状态 | 任务生命周期闭环（认领→执行→验收→回链），不含"这个知识对不对"的判断 |

关键推论：学习台和科研台是**同一层**（都评价"材料 object"，只是维度不同），工作台是**不同层**（评价"任务 object"）。学习台/科研台的活动会派生任务（"去读 X""去实现 Y"），这些任务进工作台；任务完成后，证据回流给学习台或科研台，更新对应 object 的评价——但工作台本身不产生"这个概念对不对"这类判断。

这样定义之后，"工作台要不要做成独立入口"这个反复摇摆的问题就有了确定答案：**它的对象类型和另外两个台根本不同，所以它自然不是第三个平级的内容台，而是两个台共用的执行/追责基础设施**——09-14 的收窄决定，用这个原则看是对的，只是当时没讲清楚"为什么对"。

## 3. 这个原则怎么筛选参考清单里的候选

两份清单里的项目，按这个框架至少能分到四个不同的角色槛位，不应该被当作同一份"选一个当底座"的清单笼统比较：

| 角色槛位 | 候选（来自两份清单） | 判断依据 |
|---|---|---|
| 材料/对象组织层（两台共用） | NotEMD（概念抽取/wiki-link）、agent-stack-notes（外置记忆方法论） | 处理的是 object 本身的组织与检索，不做掌握判断也不做任务判断 |
| 学习台的掌握视角 | LearnGraph（Goal→Representation→Evidence→Mastery→Action） | 链路本身就是掌握导向，天然对应学习台 |
| 科研台的研究视角 | open-science（provenance/plan-goal-review gates）、ThoughtDAG（上下文分支/裁剪） | 处理的是证据链、来源、判断演变，对应科研台 |
| 工作台的任务执行层 | PlanWeave（计划→依赖→执行→评审→反馈）、ai-project-os（capability manifest/lock、来源锁定）、Remit（checkpoint/审批历史） | 处理的是任务生命周期与验收，不含知识内容判断 |

**推论**：如果这个框架成立，"找一两个参考底座"不应该是"从24+13个仓库里选1-2个赢家"，而应该是**每个槛位最多选一个**——材料层选一个、学习视角选一个、科研视角选一个、任务层选一个（工作台既有降级为共享层的决定，任务层这一个可能优先级最低，甚至可以先不选）。这样选出来的组合天然不会互相打架，因为它们本来就负责不同的层。

## 4. 一个可以验证这个框架的回溯案例

"科研驾驶舱"R11 截图被自己的登记档（`REFERENCE_NOTES_20260915.md` §7.6）评价为"最有价值的是'一项目入口＋证据脊柱＋阶段门＋下一步'的组织方式"——这句话描述的正是**任务执行层**的形状（入口/证据/阶段门/下一步全是任务生命周期语言），不是材料组织或掌握/研究判断的形状。但它却被当成了一个独立新产品去设计（G0-P7八阶段、独立命名、独立冻结）。如果当时已经有这套 object/view 框架，"这是工作台形状的东西，不该长成第三个平行产品"这个判断本可以更早做出来——这不是巧合，说明框架本身有一定解释力，值得作为重新明晰的起点，但**这是回溯性验证，不是提前设计好再套用的，不代表框架已经完备**。

## 5. 明确留空、不在本提案里回答的问题

- 学习台/科研台"同一 object 多 view"具体怎么落到数据结构（是同一张表加评价字段，还是关联的两张表）——这是下一步真正的架构设计问题，本提案只定顶层原则，不出数据契约。
- 工作台降级为共享层之后，"任务层选一个底座"这件事优先级是否现在就要做，还是可以先放一放——工作台本来就不是当前用户想先解决的（用户想先解决学习台/科研台的底座和架构不清），不代为拍板。
- 已设计的八观察面（问题/方法/主张/谱系/团队/实现/操作/轨迹）是否就是"科研视角"的完整子结构，还是需要调整——本提案只是指出它们应该挂在"科研视角"下，不重新设计八面本身。
- R04/R05 身份问题、Bridge×RE-30 交集问题，与本提案无关，不因为开了新讨论就搭车处理。

### 7.2 对早期解释的修正与既有来源

1. **菌丝网不是谱系一面的别名。** 它涵盖知识机制、问题证据、方法迁移、人物团队、成果实现与应用、指导实践和个人成长之间的多层关系。谱系只是其中一类关系。
2. **共享对象不等于把全部结构压成一张平图再筛选。** [09-14 暂定内容版图](2026-09-14__research__multilayer-content-map-provisional-baseline.md) §1、§3 已明确多层、层内关系与跨层连接。该文件是旧“三级要求”草稿顶部指向的后续基线；层数与数据实现仍未冻结。共享身份和来源可以减少重复，但关系语义与各类评价需要分别成立。
3. **学习台不应被缩成掌握打分器。** 它也承接读材料、获得解释、补前置、练习、实现、纠错、复测、形成问题和迁移。掌握证据是结果判断的一部分，不是全部活动。
4. **工作台的共同职责不决定它必须有或没有独立页面。** [WORKBENCH.md](three-desks-v0.1/WORKBENCH.md) §1 已写明协调界面与调度内核，并保留独立交付验收职责。对象类型不同不能单独证明“只能是某种界面”；本轮继续沿已有共享服务方向讨论，不推翻或重冻结界面合同。科研项目页也可呈现工作台协调信息。
5. **四类职责不等于四个仓库。** 用户仍希望先找一两个底座。一个仓库可能覆盖多项职责，不同仓库也可能争用对象身份、数据与状态；不能声称分层后组合天然无冲突。NotEMD/LearnGraph 的当前定位只是候选，未完成整仓采用或互操作验证。
6. **不沿用已被后续稿修订的字段。** [09-11 场景 v0.3](2026-09-11__research__knowledge-network-architecture-v0.3-scenarios.md) §0 已暂不采用 `maturity`，并把 `growth_mode` 从关系永久属性移向发现/活动记录；最终选择仍开放。不能把 v0.2 中间态作为现行架构。

### 7.3 生长过程：两轮起步，之后长期多起点生长（解释提案）

| 阶段 | 主要输入与动作 | 留下什么 |
|---|---|---|
| 第一轮：以论文为临时中心 | 展开论文的问题、方法、前置、相关成果、团队、代码、评审与适用场景；范围按当前需要取舍 | 有来源的初始邻域，已知关系、待核关系和未解决问题；可用于导航但不代表本人掌握 |
| 学习期间：积累第二轮种子 | 阅读、解释、手算、实现、比较与纠错时留下疑问、失败、假设、类比和新来源 | 种子连回触发它的具体段落、推导、尝试或失败记录；随手记录不强制变成任务 |
| 第二轮：带着学后问题展开 | 按用户所说学完后的阶段，选择值得继续的种子，做定向检索、横向比较、纵向追溯、跨域迁移检查 | 修订已有关系与判断，形成新问题、候选检查或停放理由；不只是多收一圈论文 |
| 后续：由自己的问题与主线组织 | 问题、方法、团队、工业信号、开源实现或失败案例都可成为新起点 | 论文作为普通节点保留来源与历史，因新的证据或问题再次激活；其他节点同样可以激活 |

两轮是这次论文起步的节奏，不是系统终身只能执行两次，也不新设“必须把整张图学完才能探索”的门。重激活是带着新问题重访已有节点，保留前后变化，避免复制一份同名材料。

### 7.4 三个台各自负责什么（用途提案）

| 台 | 核心用途 | 与另两台的往返 |
|---|---|---|
| 科研台 | 建立并持续修订对研究世界的理解：问题位置、证据、方法、团队、成果、工业实践、候选方向及自己的研究判断 | 把理解缺口交给学习台；把选中的检索、比较、复现或验证动作交给工作台；吸收学习与实践中生成的问题和证据 |
| 学习台 | 把材料、概念和方法转化为自己的理解与独立能力；支持阅读、解释、练习、实现、纠错与迁移 | 从共享网络进入材料；积累第二轮种子；把个人尝试与研究发现分别回写，允许同一产物同时供两台引用 |
| 工作台 | 结合优先级、时间、执行者、依赖与资源协调已选择的行动，记录交付与恢复位置 | 接收明确选中的行动，把产物送回原问题；不因任务完成自动宣告研究判断成立或用户掌握 |

知识图谱强调对象和有依据的关系；菌丝网强调多起点探索与重新连接；科研地图强调问题位置与全景；团队脉络强调人物组织及时间变化。这些可作为同一系统中的工作方式和观察面，不预设每个名字都需要一个独立产品或服务。

错误记录应保留其含义：学习错题反映个人理解缺口；研究或工程失败反映特定条件下尝试的结果；复盘经验需要挂回过程和适用条件。一次本人代码写错不能直接证明论文方法无效，某个方法有局限也不自动等于本人没有学会。

### 7.5 个人主线、鲁到孙的路径与工业权重（方向提案）

用户明确要求：以进入工业界为长期导向，提高工业界关注权重，同时保持自己的主线，兼顾当前鲁侧与未来孙侧路径。

建议把三者分别表达：

- **个人主线**记录持续关心的问题、已有能力与产物，以及判断为何变化；跨论文、团队和学习阶段保持连续，具体题目可调整。
- **鲁侧与孙侧路径**记录当前可接受的训练/指导、可迁移的方法和未来想补的能力。它是主线的阶段性发展背景；不要求每个节点同时命中两组，也不把鲁组学习仅表达为去下一组的筹码。
- **工业关注权重**作用于关注、检索、比较和候选选题的优先级：实际采用、成本、延迟、可靠性、评测、部署约束、开源维护与失败经验应有更高可见度。企业来源不因此获得更高真值权重；产品宣传、工程复盘、源码证据、论文和评审仍按各自依据解释。

长期关注权重与近期时间分配分开。当前鲁侧训练、指导条件和基础建设仍影响近期安排；本轮不设百分比、不新增课程或工业工程任务。开放探索可有独立价值，不要求每条分支回流 EdgeIM，也不要求都能立即变成研究成果。

供讨论的一条候选主线表述是：**理解智能体/多智能体系统的行为与失效，研究如何建模、验证、诊断并改善其可靠性。** 这仅用于检验“鲁侧当前训练—未来形式化与可信 AI 研究—工业实际问题”能否连贯，不是已选课题、已发现空白或对两位老师当前方向的重新核实。[09-06 鲁×孙交集矩阵](2026-09-06__research__lu-sun-intersection-matrix-and-group-entry-reframe.md) 本身仍是待审草稿，内含未核来源，不将其六个候选与排序升级为已决事实。

### 7.6 对一两个参考底座的影响与下一步
