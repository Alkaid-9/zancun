## 1. 目标、非目标与验收上限

目标是在现有科研台、学习台、工作台和 Skills 上形成一个“科研项目驾驶舱”：用户能从一个项目入口看见课题、证据、阶段、产物、开放门、人工待办与下一步，并能返回真正的内容或任务正本。

本方案不把截图复刻成第四套系统：

- 不新建第二任务库、来源库、研究对象库、课程证据库或 Skill 文件库。
- 不要求所有研究按八阶段线性执行；允许跳过、不适用、并行、返回和转向。
- 不把 Skill 运行结束、Session completed、测试通过、论文产物存在、研究判断成立和用户接受合并为一个 PASS。
- 不因参考清单存在就批量安装 R01-R12；每项仍按原则借鉴、转化设计、隔离试用、正式接入或暂存处理。
- 首批不含 PDF/OCR、网页任意字符锚点、完整历史原件库、云同步、真实库迁移、后台无限搜索或无人值守写作。
- R11 身份未补前，不评价其维护、安全、数据流、实现质量或真实完成度。

方案交付只能称 `DESIGN-DELIVERED`。产品完成必须另有实际实现、技术验收、独立复核、真实用户试用和相应运行采收证据。

## 3. 划分标准

### 3.1 参考项处置

| 处置 | 入类条件 | 必需证据 | 结论上限 |
|---|---|---|---|
| 原则借鉴 | 方法能改善现有流程，不需引入软件 | 可追溯说明或机制材料 | 形成设计／检查建议 |
| 转化设计 | 具体机制有价值，但本地权威或语义不同 | 关键流程、对象、失败路径及源码证据 | 提出本地窄合同，不称已实现 |
| 隔离试用 | 文档与源码不能回答可用性、兼容或收益 | 固定版本、非敏感样本、独立目录、退出办法 | 给出采用／修改／停放建议 |
| 正式接入 | 试用与真实使用均支持，许可、数据流、维护和退出清楚 | 技术、独立复核、用户接受及运行回执 | 在批准范围内接入 |
| 暂存／不采用 | 身份不足、收益不成立、负担过高或语义冲突 | 原因、影响范围和重评条件 | 不安装、不无限调查 |

### 3.2 证据深度

按将要作出的决定使用五级证据：

1. `定位`：唯一项目、作者、版本、许可和用途。
2. `机制`：输入、输出、对象、操作及成功／失败语义。
3. `实现`：关键源码、持久化、发送、导出、恢复与测试定义。
4. `实测`：固定版本在隔离样本中的实际结果和退出。
5. `采用`：真实场景收益、维护责任、用户接受及回滚成立。

低级证据不得支持更高级结论。截图 R11 当前仅为“定位未完成＋可见界面观察”，不能进入实测或采用判断。

### 3.3 阶段门向量

每一阶段显示四个相互独立的判定门和一组正交运行事实，不保存一个模糊总PASS：

| 门 | 值 | 判定依据 |
|---|---|---|
| 输入门 | `MISSING / READY / N-A` | 必需身份、版本、材料及授权是否齐全 |
| 技术门 | `UNTESTED / RED / TECH-PASS / N-A` | 对应合同与实际测试 |
| 独立评审门 | `NOT-REQUESTED / OPEN / RED / PASS / N-A` | 有效独立回执；429或无产物仍为OPEN |
| 用户门 | `OPEN / ACCEPTED / N-A` | 用户真实操作和明确接受 |
| 运行事实组 | `local_present`、`commit_revision`、`harvest_revision`、`service_up`、`loaded_revision`、`deployed_revision`、`pushed_revision`各自为实际值／`UNKNOWN`／`N-A` | 各事实正交记录并绑定revision；`service_up=true`不能推导已加载当前commit，push也不能覆盖部署状态 |

界面可派生一句摘要，但不能覆盖门向量或运行事实。只有该阶段所有适用判定门达到通过状态，才可显示绿色“已接受”；`TECH-PASS / USER-OPEN`必须同时可见。运行事实始终按实际revision逐项显示，不参与压缩为PASS，也不能因push存在而推导loaded／deployed。

“独立评审”必须同时显示 `review_class`（至少区分 `SCOPED-READONLY / HETERO / EXTERNAL-HUMAN`）、受审对象及固定 revision／commit、reviewer 来源、是否同谱系／同一操作者、静态或运行方法、回执、时间和未查面。普通 fresh-context 只读复核通过只能称“该声明范围内复核通过”；它不等于组织独立审计、异构审、运行测试、研究结论成立或用户接受。若包要求异构审，可同时显示 `SCOPED PASS / HETERO OPEN`，不得用一个裸 `PASS` 覆盖。

### 3.4 严重度

- `BLOCKER`：越权写入／外传、来源或身份错配、关键原产物丢失、错误变绿、无法退出。
- `MUST-FIX`：核心路径、版本、恢复、导出或相关回归失败。
- `LIMITED`：不破坏核心语义，可在明确限制下试用。
- `OBSERVATION`：未测、长期效果未知或仅改善体验；不是通过，也不是自动缺陷。

### P7：单题贯穿试点

先用合成非敏感DEMO走 `课题卡→Idea评估→文献调研→论文蓝图`；技术稳定后，由用户选择一个真实、非保护问题走同一切片。之后再决定是否开章节、图表、审查和正式导出。

贯穿必须覆盖开始、暂停、重开、来源变化／失效、评审退回、用户不采用和退出。完成只证明该问题与该版本下的产品路径，不证明完整课程、多层网络或全部参考采用。

## 6. 检查、评审与验收

每个工作包固定执行：

1. **启动检查**：task_id、授权原文、仓库身份、HEAD、index/worktree、数据根、服务、写域、许可证、敏感材料边界。
2. **合同检查**：输入、输出、版本、消费者、正常／失败语义、恢复、回滚、测试命令和停止条件。
3. **实施者自测**：记录实际命令、环境、结果、失败、未测项和产物路径，不复用旧数字。
4. **主控验收**：按需求矩阵和合同逐项核，不以文件数或测试数替代覆盖。
5. **独立只读复核**：重点审权威归属、隐私、版本、恢复、证据是否支持结论；必须返回file:line与未查面，并记录review class、受审固定版本、reviewer来源／同谱系关系、方法和receipt。包要求异构或外部人审时，普通fresh-context复核不能关闭该门。
6. **用户试用**：用真实非保护样本评价卡点、误解、负担、返回与实际收益；不要求用户重复机器回归。
7. **收口**：设计、技术、独立审、用户、commit、采收、加载、部署、push分别报告。

429、连接失败或空回执不算独立证据；主线程自查不能补签独立通过。
