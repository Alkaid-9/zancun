## 第三轮：通读全部12份文件后，亲自核实的架构级发现（非转述核对，是设计判断）

以下五点均由本复核者亲自逐字核对原文得出，不是子代理转述。按影响排序。

**A. P1 承诺展示的"有效Skill运行"计数，结构性依赖尚未建成的 P4。** `RESEARCH_COPILOT_PROJECT_COCKPIT_PLAN.md` §5 P1 步骤3原文："展示原始资料、有效Skill运行、人工待办和下一步；计数必须能点回清单。"但 P4 步骤3明确说："P1页面只消费manifest；S2/S3等待S1和WP0条件。"——也就是说，在 P4 的 S1（生成运行回执manifest）落地前，"Skill运行"这件事根本没有持久、可点回溯源的记录可读，P1 想显示的"计数"要么是空的，要么是提前偷跑 P4 的范围。P1 的前置条件写的只是"G0"，完全没提"依赖P4-S1"，这是一处真实的排期漏洞，不是文字问题。**落地建议**：要么明确把 P4-S1 挪到 P1 之前作为硬前置，要么 P1 上线时这一格显式显示"N-A / 待P4"而不是显示 0（0 会被误读成"目前没有Skill在用"，而事实是"计数机制还没做"）。

**B. 驾驶舱的门派生逻辑，悄悄依赖一个自己标注"未冻结"的schema，而且这个依赖没有被写下来。** `RESEARCH_COPILOT_PROJECT_COCKPIT_PLAN.md` §2 权威对象表第一行，明确把"研究判断"列为驾驶舱要只读聚合的对象之一。而"研究判断"（`research_judgment`）这个记录类型的字段，完全由 `B_CONTRACT_PROPOSAL.md` 定义，该文件标题状态白纸黑字写着 `PROPOSED / NOT-FROZEN / NO-IMPLEMENTATION`。也就是说，驾驶舱阶段03/04的门判定逻辑，建立在一个可能还会改字段名、改证据状态枚举值的东西之上，而两份文件互相都没有点名这条耦合，更没有说"B_CONTRACT 一旦改动，驾驶舱§3.3/§4要跟着重审"。**落地建议**：这是一句话就能补的漏洞——在 G0（事实与语义冻结包）里加一条"确认 B_CONTRACT schema 冻结状态；B_CONTRACT 重开时，驾驶舱§3.3/§4强制重审"，不需要重新设计。

**C. 设计者已经用同一个技巧解决过三次同类问题，唯独第四次（P5）没有照做，原因未交代。** `goal`/`requirement`/`research_judgment` 三种新记录类型，`B_CONTRACT_PROPOSAL.md` §1 说得很清楚："复用 Object／Revision，不新建数据库"——即在 research-desk 已有的通用 `create_object(kind, attrs)` 机制上加新的 kind 值，不建新表。但轮到 P5（蓝图/章节/图表/审查/导出的"产物身份层"）时，`RESEARCH_COPILOT_PROJECT_COCKPIT_PLAN.md` §5 只说"分别保存产物引用和关系"，完全没说这些引用和关系存在哪里。这不是发明了自相矛盾的原则，而是**同一个已经验证过的解法摆在旁边，第四次没有照抄**，也没解释为什么这次不适用。**落地建议**：P5 大概率应该照抄同一个模式——加一个新 Object kind（比如 `manuscript_artifact`），不新建store——设计文档里应该把这句话明写出来，而不是留白让"是否在建第四套正本"这个问题悬而不决。

**D. 从未评估过成本最低的替代方案，而这个替代方案的原型其实已经在用户自己的仓库里跑着。** 全文12份文件搜索"静态生成/无状态/轻量替代/不新增数据库"，零命中——这条路线从未被列入比较对象。但 `research-desk/README.md` 自己的首页机制就是这个模式的现成范例："科研台_CURRENT.md"是"生成的人类固定入口"，不需要启动服务、不需要新schema、每次重新生成即可查看当前状态。P1 设计的却是一个"低保真交互"页面（有"桌面/窄屏可用"这类UI验收标准），这比验证"聚合视图是否真的有用"这件事所需要的复杂度要高。**落地建议**：在写 P1 的任何页面代码之前，先花很少的成本照着"科研台_CURRENT.md"的生成器模式，产出一份"科研驾驶舱_CURRENT.md"——读取 Topic/Question/研究判断/task_logs/Skill manifest，渲染成八阶段表+五门向量的纯 Markdown。这个东西造价接近于零（复用现成生成器），天然满足"不新增schema"，而且直接把草稿本身提的"是否接受v0完全只读"这第2个悬而未决问题，从"用户先验拍板"变成"先做一版最便宜的验证，拍板建立在实测上"。如果这份静态页确实减少了切换负担，再升级成交互页是风险小得多的第二步。

**E. "独立评审门"其实有一套贯穿全语料的操作性约定，只是没有写成一条正式规则，而这套约定本身有一个值得点名的认知天花板。** 通读12份文件后发现，"只读子代理"这个机制在全部文档里被反复使用作为"独立评审"的具体操作方式（例如 README.md"只读子代理因429未产出证据"、WORKBENCH_LINK_REVIEW.md"来源：只读子代理...终态complete"）——是谁来评、怎么算通过，其实有稳定共识：换一个独立的只读子代理实例重新看一遍，必须给出 file:line，429或无产出记为 OPEN 不算 PASS。这套约定不是空的，只是没有被单独写成一条正式定义。但值得指出：这个"独立"评审，是同一个主控会话派生出的子代理，读同一份磁盘，受同一个操作者调度——它在"程序上独立"（全新上下文、看不到主线程的预设立场），但不是"组织上独立"（没有另一个有权说不的外部主体）。语料库自己对这一点是诚实的（用 `SCOPED-STATIC-REVIEW-PASS` 这种降级措辞，不虚报成完整审计），我提出来只是因为驾驶舱把"独立评审门"做成一个会显示颜色的UI状态后，未来看到绿色 PASS 的人可能会误读成比"同一操作者名下的子代理复读了一遍没意见"更强的东西。**落地建议**：机制不用改，建议在这道门的UI提示文案里显式写清楚"独立"具体指什么（全新上下文、只读、同一操作者），不需要新设计。

## 值得肯定、不应该被重新设计的部分

- 五门模型明确拒绝把"Skill运行完成"直接等同于"已接受"，而且在实践中真的做到了——`WORKBENCH_LINK_REVIEW.md` 把结论主动降级标成 `SCOPED-STATIC-REVIEW-PASS` 而不是虚报成完整通过，这是知行合一的证据，不只是写在纸上的口号。
- 明确规定429或无产出记为 OPEN、不算通过，不允许"审查者没回应"被悄悄读成"没发现问题"——这条和用户自己的历史记忆（[[openrouter-subagent-402]]）里"子代理通道429/402双墙"的教训是同一课，这次设计里被正确地制度化了。
- 参考材料的五级证据阶梯（定位→机制→实现→实测→采用，"低级证据不得支持更高级结论"）是一套可以脱离这个项目复用的通用方法论，和"截图不能证明功能在跑"是同一种纪律，而且被系统性地执行了，不是说说而已。
- 用 research-desk 已有的通用 `create_object(kind, attrs)` 机制去承载 goal/requirement/research_judgment 这三种新概念，而不是新建表，这个直觉是对的——只是没有被贯彻到 P5（见发现C）。
