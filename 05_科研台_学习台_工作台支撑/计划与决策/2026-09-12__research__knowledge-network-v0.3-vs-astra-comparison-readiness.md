## 1. 结论先行

Astra v0.1 §7 给出九个比较问题。逐条核对两份场景稿原文（非按摘要转述）后判断：六到七条已有可以直接采纳的共同结论；两到三条是双方都尚未拍板、需要用户判断的真实取舍点，不是可以由任一方单独决定的"谁更对"。

已有共同结论的几条中，三条证据最扎实，值得点名：
- `SourceRef` 缺网页锚点支持（两稿独立发现同一缺口，Astra §7 表述为"网页全链合同待补"，v0.3 §4 表述为"最快会撞到的真实阻断点"）。
- 指导库"推荐/选用/生效"需要一条正式关系而非一个标签（Astra §7"推荐、选择、实际过程、反馈分开"；v0.3 §3 明确证伪了 v0.2 自己"指导库只需 dimension_refs 标签"的说法）。
- 现在不急着造通用 Event 对象平台（两稿都提出"先定字段语义、有真实样例再定是否需要独立对象"，未各自新造一层）。

这三条不是"两边商量出来的"，是各自独立从不同场景走查压出来的同一个缺口——这类独立复现的分量比一方提出、另一方附议要重。

## 2. 尚未拍板的分歧点

### 2.1 轻量观察是否要拆成独立类型

Astra 原文（§2 场景B）："不能把所有观察活动塞成一次Attempt……但不用'我做了一次尝试'假装'我看见了一条信息'"——倾向观察与尝试终将分开，先不冻结是否新增 kind。

v0.3 原文（§2 场景B）："本稿倾向不到必要不新增类型——先尝试用`Attempt`+一个能区分'这是扫描记录还是学习尝试'的字段……如果实践中发现两者需要的必填字段差异太大导致同一张表要塞进两套不相关的必填项，再考虑拆出新kind。"

两稿方向不同（Astra 偏向"终将拆"，v0.3 偏向"能合就合"），但双方都明确写了"这是留白，不是本稿的最终判断"。这是真分歧，不是哪边没想清楚——判据在于实践中 breadth_scan 与 depth_dig 的必填字段差异有多大，这需要真实案例喂出来，两边现在都没有真实案例可看。

### 2.2 v0.3 场景A 比 Astra 场景A 单薄

Astra 场景A 的采用记录是一个显式八字段对象（参与产品版本/采用对象/采用程度/条件/发生时间/获知时间/来源断言/后续更正），并且走了一个具体反例：厂商更正"不是M，只是另一种摘要"时，新更正引用旧断言、旧记录保留、相关研究判断需复核但不自动删除用户已完成的学习记录（§2 A4/A5 + 场景验收表第3行）。

v0.3 场景A 只有一条关系边 + 一个候选问题节点，完全没有走反转测试用例，并且自己承认"`产品X→方法M`该用什么relation_type，`result_of`是否语义相容——这一点我没有把握，只是猜测语义相容，不是确认过的结论"（v0.3 §1）。

这条不是分歧，是我这边的覆盖缺口，应如实标注，不该包装成"两种同样成立的设计选择"。

### 2.3 严谨度不对等

Astra 每个场景都带一张"场景验收与反例"表，主动构造试图打穿自己提案的反例（如上述厂商更正场景）。v0.3 的对应部分是"暴露的具体缺口"清单,更偏罗列已发现的问题，没有主动构造反例去检验提案本身扛不扛得住。

这意味着即便表面结论一致（如 SourceRef 缺口那三条），两边结论背后的确信程度也不对等——Astra 那三条经过了反例尝试仍然成立，v0.3 这边只是"看出来有这个问题"，还没有试过用反例去戳它。写比较表时如果把两边并列成同等重量的证据，会掩盖这层差异。

## 4. 与纠错本讨论的关系

本轮讨论中，用户提出的"纠错本要先有真实案例才能验证分类规则"这一判断（见 [纠错本整合稿](2026-09-12__learning__correction-notebooks-and-growth-v0.1.md) §10），与本节 2.1 的判断结构相同：轻量观察是否该拆类型，同样要等 breadth_scan 与 depth_dig 各自出现几次真实记录后才能看出必填字段差异有多大，不是设计阶段能单方面判定的。两处都指向同一个更上层的原则——多处场景设计的分歧，只能靠积累真实使用案例来收敛，不能靠继续纸面推演分出胜负。
