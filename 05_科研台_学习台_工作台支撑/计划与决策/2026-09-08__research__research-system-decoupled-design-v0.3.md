## 1. 先确定系统边界

旧方案把“科研台产品、研究内容和 MAS 工程仓库”放在同一写域，短期接入方便，长期会产生三个问题：代码审查会扫到大量私人材料；科研记录和执行日志的生命周期不同；移动或上服务器时难以判断什么必须一起迁移。新方案把**职责解耦**作为第一原则，连接依靠稳定 ID 和显式引用。

```text
科研台应用（代码） ──读取／写入──> 学习科研内容库（权威记录）
        │                                  │
        │                                  ├─ 来源与文献登记
        │                                  ├─ 学习／探索／研究记录
        │                                  ├─ 七图关系与地图裁定
        │                                  └─ 便携导出
        │
        ├─ 查询／展示 ──> 每个内容库自己的派生索引
        │
        ├─ 研究问题／执行请求 ──引用──> 工作台应用（代码）
        │                                  │
        │                                  └─ 项目仓／实验产物／测试事实
        │
        └─ 运行事件 ──追加──> 独立运行日志库

+ 部署配置／密钥（服务器私有，不进 Git）
```

科研台回答“我在研究什么、依据是什么、理解怎样变化、哪些关系可复用”；工作台回答“执行了什么、代码和版本是什么、结果能否复做”；项目仓回答具体研究项目的代码和实验事实；日志库回答“系统何时以何配置做了什么”。它们可以互相链接，但不共享一个总状态机。

## 2. 推荐的仓库／目录分工

最终名称可调整；以下先用职责名，避免先为目录命名再反过来迁移内容。

| 区域 | 权威内容 | 是否可给 GPT 代码审查 | 典型备份／迁移单位 |
|---|---|---|---|
| `research-desk-app` | 科研台 UI、读取／写入协议、索引器、适配器、文档 | 可以；不放私人原文、密钥和运行数据 | Git 提交＋版本说明 |
| `research-knowledge` | 来源登记、原文／附件索引、学习会话、菌丝关系、地图裁定、研究问题与决定 | 默认不直接公开；按需导出脱敏样例 | 内容库快照＋附件清单 |
| `research-projects/*` | 一个研究项目一个仓：代码、实验合同、输入说明、结果和项目报告 | 可以单独授权；每仓自洽 | 项目仓提交＋实验产物归档 |
| `workbench-app` | 工作台界面、任务／执行协议、Git 与验收适配 | 可以；不放项目私有结果 | Git 提交＋运行说明 |
| `research-logs` | 应用事件、任务执行事件、服务器运维事件、错误与审计索引 | 可审代码相关的结构化日志；正文和凭据分离 | 按月归档的 append-only 文件 |
| `research-runtime`（服务器私有） | SQLite 派生索引、缓存、队列、上传临时区、服务配置 | 不作为代码仓链接目标 | 可重建索引＋备份快照 |

首版不要求立刻建立六个远端仓。先在本机用职责清晰的根目录和相对引用验证一个贯通场景；确认写入、搜索、迁移后，再决定哪些仓需要独立远端。`MAS_Safety_Project` 继续作为现有历史工程与台账的权威，不在本轮把它强行改造成新科研台。

### 2.1 内容库的建议结构

```text
research-knowledge/
  README.md                    # 内容库规则、ID、来源和备份说明
  registry/
    sources/                   # 论文、讲义、会话、网页、代码版本登记
    identities/                # 同文异名、版本与人工裁定
    people-teams/              # 人物、团队、机构和时间关系
  records/
    learning/                 # 学习会话、作答、提示、理解变化
    observations/              # 开放探索和领域观察
    research/                  # 问题、假设、比较、决定、研究判断
    relations/                # 有依据的关系；不把图布局当事实
    mycelium/                 # 可复用节点卡和反例卡
  maps/                       # 五层／七图的视图定义和人工裁定
  attachments/                # 仅纳入范围的原件或外部对象指针
  exports/                    # 手机包、脱敏包、交接包
  schemas/                    # 文件格式版本
```

大 PDF、视频和原始聊天可以另放 `research-materials` 或现有资料根；内容库只登记稳定 ID、版本、相对位置和定位信息。不要为了“统一”复制一份大型原件。

### 2.2 日志分层

“日志”不是一种东西，至少分四类并分别决定保存期限：

| 类型 | 例子 | 权威位置 | 能否删改 |
|---|---|---|---|
| 研究证据 | 原话、手算、代码结果、来源摘录、反例 | `research-knowledge/records` 或项目仓 | 保留修订关系，不静默覆盖 |
| 决策／交接 | 方案版本、停点、范围、恢复入口 | 内容库或 MAS 台账 | 按正式交接规则写入 |
| 执行事件 | 任务 ID、命令摘要、版本、测试与产物路径 | 项目仓任务记录＋`research-logs` 索引 | 追加；错误以更正事件记录 |
| 应用／服务器运行 | 启停、请求、错误、资源和备份结果 | `research-logs`／服务器私有轮转文件 | 追加、轮转；不得写 token、cookie、原文全文 |

代码仓只保留能解释行为的日志 schema、示例和回链；运行日志正文不因 GPT 能连接代码仓就全部放进代码仓。研究证据也不能被普通 HTTP 访问日志替代。

## 3. 稳定引用与最小数据模型

跨仓引用采用稳定 ID，而不是绝对路径。建议形式：`src:edgeim-icws-2025`、`sess:2026-09-08-recursion-01`、`q:interaction-summary`、`run:TASK-...`。每个对象至少有 `id`、`kind`、`title`、`revision`；需要时增加 `source_refs`、`created_at`、`status` 和 `supersedes`。

```yaml
id: sess:2026-09-08-recursion-01
kind: learning_session
revision: 1
track_refs: [T, F]
source_refs: [src:edgeim-icws-2025, src:lecture-cut-recursion]
ability_observation: prompted_step
research_status: none
next: 独立走一个改变条件的 cut 例子
```

三种状态轴分开：

1. **工作状态**：计划、进行、完成、暂停；回答交付是否发生。
2. **本人表现**：看过、示范后、提示下、独立完成、跨题复用；回答具体证据支持到哪里。
3. **研究判断**：观察、待查、PARK、候选、研究中、否定、结案；回答问题是否值得继续。

科研台不能因为用户读过一篇论文就写成 `ability=owned`，也不能因为一项任务完成就写成 `research=contribution`。AI 摘要、用户原话、论文原文和代码结果分别标注。

## 4. 学习体系与科研体系怎样共用而不混淆

长期体系继续使用 `WORLD/FIELD → RESEARCH MAPS → ACTIVE TRACKS → EVIDENCE/PRACTICE → ARTIFACTS`。七图是同一批对象的七个观察视角，不建立七份重复正文。T（论文）、F（基础）、R（自主研究）、E（生态观察）是工作标签；鲁组进组是当前 campaign，不是整个体系。

论文＋AI 带学继续作为默认方式：从真实问题进入，必要时补连续基础单元；讲义和课程用于定义、练习和长期覆盖；视频用于过程示范。F 保持独立目标，不能永远等论文暴露缺口；R 可以从 P 并发／死锁或 O 对象／交互入口试探；E 可以有不服务当前项目的观察。

每次学习只要求最小记录：当前问题、触发来源、实际动作／提示、理解变化、下一步。只有当内容值得跨问题复用时，才提炼成 Mycelium Card。卡片按需加入 `pressure`、`representation`、`downstream`、`preserve/lose`、`assumption`、`failure`、`genealogy`、`my_action` 等字段；不把完整卡强加给每次听课。

表示类问题可以比较五个维度：`expressiveness`、`sufficiency`、`identifiability`、`stability`、`scalability`。它们是分析维度，不是自动评分。尤其要区分“对某个下游判断够用”和“从观察唯一恢复真实结构”。

## 5. 科研菌丝网的运行规则

菌丝网是“问题和证据的连接层”，不是自动生成的百科全书。一个节点可向前置、下游、替代、谱系、反例、工具和下一问题生长；同一证据只保存一次。

```text
观察／卡点
  → 对象与来源
  → 当前理解或失败
  → 反例／手算／最小实现
  → 横向比较与 prior-art
  → 是否仍有具体 residual
  → PARK / 继续学习 / 进入研究任务
```

研究候选经过四个检查才可进入项目任务：`failure`（确有失败）→ `evidence`（对下游判断有后果）→ `prior-art`（相近工作未直接解决）→ `executable contribution`（能以当前资源做最小验证）。没有通过的内容仍可作为观察保存，不删掉也不包装成创新。

目前应保留的研究候选：PARK-A“交互语义与分布式轻量表示的取舍”、PARK-B“面向下游的 sampling adequacy”、PARK-C“按性质选择表示的充分性”。它们是候选，不是已选题。`Identifiability ≠ Sufficiency`、edge-specific lag 等新观察先入 WATCH／概念节点，待原件和反例支持后再升权。

## 6. 人、Agent 与系统能力必须分层记录

用户补充了一个关键事实：个人基础能力可能暂时弱于“用户＋模型＋材料＋工作流”共同产生的结果，但对 AI 的拆解、调度、上下文组织和互审也构成真实能力。科研台不能把系统产出直接记成个人掌握，也不能把人机协作的有效配置抹掉。

因此每次工作至少记录三层：

| 层 | 回答的问题 | 典型证据 |
|---|---|---|
| Personal capability | 不依赖强模型时，用户能解释、修改、预测和迁移到什么程度？ | 独立手算、改输入后的预测、错误诊断、跨题复用 |
| Orchestration capability | 用户能否选择模型、拆任务、给上下文、设置停止条件并组织互审？ | 任务分解、提示／上下文设计、模型分工、冲突裁决 |
| Human–AI system capability | 在明确的模型与工作流配置下，系统实际完成了什么？ | 可复做产物、Agent 回执、版本、人工验收和失败记录 |

系统能力是有效的工作能力，但不自动等于个人领域能力。个人能力不足也不是“什么都没有”；它说明当前需要把验证、解释和迁移债务补上。记录中使用 `execution_mode`（`human_only`／`human_ai`／`agent_assisted`）、`verification_level` 和 `contribution_roles`，不再用一个分数代替三层。

科研台和共同画布显示产物来源标记：`agent_proposed`、`user_directed`、`user_edited`、`user_verified`、`independently_reproduced`。Agent 在画布上新增的卡片和连线先是 proposal；用户接受不等于已经独立理解，后续验证记录另存。

轻量自测不要求每次脱离 AI 重做全部任务，而是抽查三个问题：能否解释为什么这样做；能否构造一个失败反例；AI 给出相反答案时能否判定依据。三个都不能做，记录为主要依赖系统；能解释并造反例，说明部分内化；还能裁决冲突并迁移到新问题，才提高个人能力证据等级。不同任务可以采用不同抽查深度。

这会改变任务线和画布的呈现：同一个任务可以显示“系统完成、个人验证未完成、研究判断仍待核”，而不是简单变成绿色 DONE。工作台记录模型与执行事实，科研台记录用户实际理解和验证，二者通过同一个 `run_id`／`evidence_id` 连接。

## 7. 应用之间的接口

科研台向工作台提交一个执行请求时，至少带：`question_id`、目标、输入来源 ID、允许写域、预期产物、停止条件、验收方式。工作台返回：代码版本、实际命令摘要、运行结果、测试／失败、产物路径和 `run_id`。科研台只根据回执更新 Evidence，不复制整份运行目录。

TaskQuay 放在工作台执行接口一侧：先在独立沙盒完成真实委派闭环，再讨论访问科研项目；它不负责判断学习通过、研究新颖性或把手机材料自动上传。另一账号仍按人工文件包交接。

## 8. 本地与服务器部署

### 8.1 本地优先阶段

先运行一个科研台进程，内容库和项目仓保持普通文件；每个内容库生成自己的 SQLite／FTS 派生索引，索引损坏可删除重建。SQLite 不成为唯一真相源，也不让数据库事务替代 Git／文件修订。

首个运行切片只做四件事：打开“继续”入口、登记一个来源、保存一条学习／观察记录、按中文短词和 ID 找回它。通过关闭重开、重建索引和导出快照验收后，再接七图和工作台。

监听默认回环地址，配置文件显式写出内容根、索引根、端口和日志根；不扫描整个 D 盘，不把密钥写进仓库。首版不依赖向量数据库；语义召回作为后续可替换适配器。

### 8.2 服务器阶段

服务器只承载选定的应用和派生索引；原始大资料可按备份／同步策略保留在本地或独立对象存储。先做单节点部署，再评估是否需要第二节点。必须先决定：哪些内容同步上去、谁能访问、备份频率、恢复演练、日志轮转和成本上限。Oracle 未申请成功或购买 VPS 都不改变这些边界；服务器选择是部署决策，不是当前架构默认值。

推荐同步方向是“本地内容库提交／备份 → 服务器只读或受控写入 → 回收变更前审阅”，避免两边同时编辑同一 Markdown。运行日志服务器本地产生，按月导出索引；密钥只在服务器 secret store／权限文件中。

## 9. 迁移顺序与回退

迁移不从移动全部资料开始，而按风险递增：

1. **冻结清单**：列出现有来源、记录、地图、项目和日志的权威位置，标注重复／派生／未知。
2. **先建协议**：稳定 ID、相对引用、来源定位、状态轴、写域和备份规则。
3. **复制少量样本**：EdgeIM 一篇原文＋一条真实学习记录＋一个开放观察；原件保留不动。
4. **实现 D1 切片**：保存、重开、中文搜索、导出、索引重建；人工检查引用。
5. **接 D2/D3**：菌丝关系、W5 只读适配、一个工作台执行回链。
6. **逐类搬迁**：先记录，再地图裁定，再项目附件；每批有清单和回退点。
7. **服务器复制**：本地快照可恢复后再上机；演练从文件重建索引和页面。

任何阶段失败，删除新派生索引或新仓样本即可回到原位置；不删除原资料，不用整树 reset／clean。旧 MAS 台账继续按自身规则维护，直到新系统实际接管某类内容并有迁移回执。
