## 0. 触发与当前判断

用户原话：

> 我在想我们的科研台应该怎么设计，我觉得独立于工作台会好一点，因为科研台太大了，科研台我希望是能把我们的自己的map框架、搜索、整理、文献笔记、科研团队的脉络、横向对比的那个也加进去、还有一些别的功能，所以我觉得独立出来比较好

当前方向：科研台倾向于作为独立产品和独立研究空间设计，不再把它当作工作台的附属面板。这个方向尚未冻结；“独立”首先指产品边界、信息架构和研究数据模型独立，不等于复制一套通用任务执行器。

本档承接此前 `2026-09-04__research__luo-pengsida-fusion-workbench-mount-alignment.md` 中仍悬空的 Q1。此前 Q1 是“工作台 v2 还是独立科研台”；本次用户已明确表达偏向独立科研台，但尚未完成正式方案审批。

## 1. 为什么独立更合适

工作台的主对象是：

```text
项目 -> 任务 -> CLI/Agent 会话 -> 执行 -> diff/测试/验收
```

科研台的主对象是：

```text
研究问题 -> 来源/论文 -> 笔记 -> claim -> evidence
         -> map relation -> 横向比较 -> 决策/实验
```

地图、文献、团队谱系和比较矩阵不是工作台的附属功能，而是科研台自身的领域对象。若继续塞入工作台，研究对象会退化成任务页旁边的面板，搜索、脉络和证据之间也难以形成统一模型。

## 2. 候选产品边界

科研台拟独立拥有：

- 研究总览：当前问题、阅读队列、待核 claim、近期决策；
- 全局搜索：本地文献、笔记、人物、团队、项目和关系；
- 文献库：PDF、元数据、版本、来源、阅读状态和引用；
- 研究笔记：摘录、页码锚点、纸面分析、证据审计；
- 自有 Map：知识、方法、思想谱系、迁移、能力和成长视图；
- 横向比较：论文、方法、团队、实验设置、指标和证据矩阵；
- 团队脉络：人物、实验室、合作关系、论文、时间线和置信度；
- 研究议程：问题、假设、竞争解释、实验计划和决策；
- 导出与互操作：Markdown、JSON、CSV、BibTeX，以及到工作台任务的链接。

工作台继续拥有：代码执行、CLI 会话、任务状态、Git/worktree、测试、变更审阅和交付验收。科研台通过研究问题、证据包、实验计划和执行链接连接工作台，不共享整套界面和状态机。

## 3. 研究对象主链

```text
Question
  -> Source / Paper
  -> Note
  -> Claim
  -> Evidence
  -> Map Relation
  -> Comparison
  -> Decision / Experiment
  -> Workbench Task
```

人物、团队、实验室、方法、项目和时间线作为可关联对象接入这条主链。AI 生成的实体、关系和摘要先进入候选状态；经过用户确认并绑定来源后，才进入稳定研究记录。

## 5. 仍有优化空间的关键问题

1. **独立到什么程度**：独立仓库、独立数据库、独立进程是否都需要；哪些基础能力可通过接口复用，避免重复造任务系统。
2. **规范对象模型**：Paper、Source、Note、Claim、Evidence、Person、Team、Method、Relation 的最小字段和稳定 ID 如何定义。
3. **Map 的真相关系**：地图是稳定关系的视图还是可编辑对象；关系的来源、置信度、时间和撤销如何保存。
4. **搜索与证据链**：全文检索、语义检索、网页来源、PDF 页码、版本差异和检索结果如何回链，避免“搜到”被误当成“核实”。
5. **团队脉络**：合作关系、机构隶属、论文谱系和机制类比必须分开；历史关系与当前状态不能混在同一条边上。
6. **横向比较**：比较维度由谁定义；论文自报指标、复算结果、个人推论和未知如何并列而不混量纲。
7. **AI 介入方式**：哪些动作可以自动候选化，哪些必须用户确认；如何保留原文、提示、模型、时间和修改记录。
8. **P0 切片**：第一版应验证一条真实研究闭环，不能一开始同时做完整地图、团队知识图谱、自动检索和协作平台。
9. **互操作与退出**：所有核心记录都要能导出为普通 Markdown/JSON，不能被某个前端或向量库锁住。
10. **许可证与来源**：外部仓库只作参考；已有记录显示 Reviva 和 NotEMD 的试用/整合边界不同，任何代码或内容复用必须重新核验许可证和授权。

## 6. 候选 P0 纵向切片

用 EdgeIM 做第一条可验收路径：

```text
导入论文
 -> 建立来源与论文记录
 -> 写 Paper 分析笔记
 -> 建立带页码的 claim/evidence
 -> 挂到知识/方法/谱系 Map
 -> 与 sigRank、CrossEdgeIM 做一张比较表
 -> 导出 Markdown/JSON
```

团队脉络、自动网页检索、复杂交互图和多用户协作列为后续增量，是否进入 P1 需要在设计阶段按实际使用价值排序。

## 7. 初步验收标准提案

- 不启动工作台运行时，科研台仍能打开、搜索、阅读和导出自己的研究记录；
- 一篇论文可以从来源记录走到笔记、claim、evidence、Map 关系和比较表；
- 每条稳定关系都能回到来源或明确标为推论/假说/UNKNOWN；
- AI 生成内容不会直接覆盖用户记录，候选关系可审阅、修改和撤销；
- 地图、比较和团队脉络是同一对象模型的不同视图，不维护多套互相漂移的副本；
- 研究台可以把实验或执行请求交给工作台，并能回链结果、版本和证据；
- 核心资料可导出，不依赖某个 UI 才能恢复。

## 9. 用户方向确认（2026-09-05）

用户补充：

> 感觉独立好点，然后和工作台、Obsidian/Reviva 那些 打通

方向收拢为：`INDEPENDENT-RESEARCH-DESK + BRIDGES`。

- 科研台独立拥有研究对象、证据链、Map、搜索和研究脉络的产品边界；
- 工作台继续负责任务执行、CLI/Agent 会话、代码、Git、测试和交付验收；
- Obsidian/Reviva 作为可互操作的资料与笔记端，优先通过普通 Markdown、PDF、BibTeX、JSON 和稳定 ID 打通；
- P0 不做三个系统之间的实时双向覆盖同步，先做可追溯的导入、导出、深链接和单向提升；
- 科研台中的结构化 claim/evidence/Map 关系必须能够回到文件或来源，任何 AI 生成关系先为候选状态。

### 9.1 仍需优化的桥接问题

1. **权威归属**：建议“人类可读文件保存正文与来源，科研台索引保存结构化关系，工作台保存执行事实”，避免三个数据库互相覆盖。
2. **同步方向**：先规定 `source file -> research desk index`、`research decision -> workbench task` 和 `workbench result -> evidence link` 三条方向；P0 暂不做任意字段双向合并。
3. **冲突处理**：使用稳定 `entity_id`、来源版本和变更记录；发现同一对象多处修改时进入待审队列，不静默覆盖。
4. **Obsidian/Reviva 适配**：先适配开放文件结构和链接格式，不依赖某个应用的内部数据库或私有 API。
5. **体验连续性**：用户应能从一条文献笔记跳到 claim、Map、比较表和工作台任务，也能从执行结果回到产生它的研究问题。

本次方向确认仍不是技术栈或页面实现授权；下一步继续做接口和对象模型设计。
