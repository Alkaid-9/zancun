## 2. 统一工作流：六步而不是四套流程

下面的六步是把三源机制接到 OS 的最小适配；文中的 L0–L5 是 B4 proposal 的挂载标签，不表示冻结 OS 已批准这些层。每步都规定“用户先产生什么”，再规定 AI 可以做什么。

### Step 0｜定边界（适配标签 L0）

先写清楚对象、来源和当前 claim ceiling：

- 这是讲义的建议、论文的原文、自己的推断，还是尚未核验的图/链接？
- 目标是读懂、重实现、做小实验，还是写作表达？
- 哪些页面/图像可读，哪些只能记为 `[需验证]`？

输出：一行 source/provenance 表和一个“现在不能说什么”栏。没有这一步，后面的新颖性、实验和写作判断都降级为讨论。

### Step 1｜先判问题（适配标签 L1）

用 Luo PDF 的新/老问题区分和 SS 的类型二分，但不作评分：

1. 这是已有清晰定义的问题，还是由新需求/新技术带来的问题？
2. 一句话写 What：对象、输入、输出和边界是什么？
3. 一句话写 Why：实际需求、已有局限或观察是什么？
4. 若是新问题，是否有真实场景、可获得数据和可衡量结果的候选证据？
5. 若是老问题，改进轴是性能、准确率、通用性、成本、场景还是约束？代价是什么？

来源提示：Luo PDF p.9、p.12–22；SS M3/M5/M10/M12；pengsida `Research Project` 摘录第 1–5 步。

输出：用户填写的 `problem_card`，而不是“值得发论文”的 verdict。

### Step 2｜广度到深度（适配标签 L1/L2）

- 找方向：先广读，抓 idea、问题类型和领域地图；不在第一遍假装掌握细节。
- 方向收窄：再深读实验、数据、代码、关键假设和失败边界。
- 打开论文前先列 3 个问题；读完再用 What/Why/How/So What 对照。
- 找出论文的 running example；没有合适例子时，用户自己造一个最小例子。

来源提示：Luo PDF p.23–25、p.36、p.42；SS M7–M11/M17；原有 `PAPER_READ_TEMPLATE.md` Stage 0–2；pengsida 的 literature-tree 线索。

输出：带页码的 paper note、三问答案、箭头链条和一处最小例子。AI 可以定位原文和指出缺口，不能替用户填答案。

### Step 3｜先做小实验，再解释失败（适配标签 L2/L3）

把 pengsida 的实验/调试链和 Luo PDF 的“方法—实验评估”链接起来：

1. 先写 prediction：预期哪一个现象变化，若相反先怀疑什么？
2. 用 toy 或最小 setting 保留一个要研究的 technical challenge。
3. 一次只改一个因素，记录输入、代码版本、参数、结果和图。
4. 分开收集 good cases 和 failure cases；先找能工作的版本，再逐步加复杂度。
5. 列出多个可能原因并排序；逐项用观察或实验排除，而不是凭感觉修。
6. 修复后复跑原失败 case，并记录替代解释仍是否可能。

来源提示：pengsida `方法论/04实践：代码能力、实验能力、分析实验不work的原因的能力.md`、`skills/EXPERIMENT_DESIGN.md`、`skills/DEBUG_METHODOLOGY.md`；Luo PDF p.17、p.27–29；SS M4/M15/M16。

输出：prediction、最小实验表、failure/good case 表和原因验证记录。所谓“快速迭代”只有在这些记录存在时才算有效。

### Step 4｜把理解组织成可读结构（适配标签 L2/L5）

论文或报告写作先由用户组织逻辑，再用 AI 做局部核对：

- 摘要：What → Why → How → contribution → result；
- 引言：动机/背景 → 问题 → 核心观察 → 技术贡献与结果；
- Overview：先总后分，说明 workflow、module 目的和后文锚点；
- 技术段：先解释为什么设计，再给形式细节、伪代码/公式和例子；
- Related Work：忠实概括、指出具体差异、承认贡献，不曲解；
- 结论：总结贡献，避免机械重复引言；
- 图：让读者能从图和 leading text 复原主线，符号与正文一致。

来源提示：Luo PDF p.34–64；SS M7–M9/M13–M16；原有 `05写作.md`、`PAPER_READ_TEMPLATE.md` 和写作 skill 子模块。

特别边界：Luo PDF p.61 的“初稿不要直接由 ChatGPT 生成”与 OS 的 ownership-first 一致；AI 可做语法、格式、检索和局部一致性检查，但不能代替用户组织核心 reasoning。

### Step 5｜审查而不是自动判分（适配标签 L3/L4）

用 Luo PDF p.68 的四个 reviewer 关注点和 SS M1/M15/M19 做问题清单：

- Novel Problem：问题定义和重要性证据在哪？
- Novel Method：方法相对已有工作改变了什么？
- Nice Story：What/Why/How/So What 是否互相对应？
- Nice Presentation：图、符号、结构是否让读者能复原？
- 实验：baseline、setting、指标、消融和替代解释是否足够支撑当前 claim？

每一项只产生“证据/缺口/待核验”三类结果，不生成 Strong Accept/Reject，不把审稿人的偏好当作用户能力结论。

### Step 6｜ownership 收口（适配标签 L4/L5）

关掉答案和对话后，用户必须能：

- 脱稿复述问题、representation 和关键假设；
- 改一个条件或换一个例子，并预测影响；
- 解释一个失败结果和至少一个替代解释；
- 重画关键图或把公式实例化；
- 在 D+2/D+7 冷启动后重新接管；
- 指出哪些来自 PDF/论文、pengsida、SS、AI、现有代码和自己；
- 把结论写到 evidence 允许的上限。

通过后才写入 Hard Evidence Ledger；没通过则进 Mistake Log 或标为邻接/外围知识。

## 3. 一页纸操作卡

每次读论文、做小实验或准备汇报时，按下面顺序填写；空白项不由 AI 代填。

| 栏 | 用户先写 | AI 可协助 | 证据位置 |
|---|---|---|---|
| 对象与来源 | 研究对象、PDF/论文页码、代码版本 | 检索和定位 | L0 source 表 |
| 问题类型 | 新问题 / 老问题 / 暂不能判 | 提供相邻定义供比较 | problem card |
| What/Why | 各一句话及原文出处 | 检查是否漏项 | paper note |
| 关键挑战 | 方法真正要跨过的障碍 | 反问 naive 方案 | challenge 表 |
| 预测 | 结果前的方向性预测和理由 | 找反例、提醒混杂因素 | experiment log |
| 最小实验 | 一个变量、输入、baseline、指标 | 机械运行和格式整理 | experiment table |
| 失败解释 | good/failure case、候选原因排序 | 对照代码/文献、提出追问 | failure log |
| 结构与图 | 先总后分、重画一张关键图 | 查符号、引用和语法 | outline/figure |
| claim ceiling | 当前最多能说到哪 | 扫描证据缺口 | ledger / note |
| 冷启动 | 变体、反例、D+2/D+7 日期 | 出题和记录，不透露答案 | acceptance record |

## 4. 与现有材料的去重关系

### 4.1 不新设第四套论文模板

本卡使用原有 `方法论/PAPER_READ_TEMPLATE.md` 作为落笔位置，只增加三类字段：

1. Luo PDF 的问题类型、What/Why/How/So What 和广度→深度顺序；
2. pengsida 的 prediction、toy、good/failure case、一次只改一处；
3. OS 的 source/provenance、claim ceiling、ownership 和冷启动。

SS 的 M7–M17 是提问和检查的来源，不另复制一份同结构模板。

### 4.2 不把三库的重复内容相加计数

- `research_growth` 的 `02阅读/03创新/04实践/05写作` 已经包含 pengsida 摘录和 skill 化版本；本卡只做入口和映射。
- SS handbook 的 PDF 是 SS 的一个来源件，不是第五个独立核心仓库。
- 现有 OS 的三本账和冷启动规则仍是约束；B4 的 L0–L5 目前只是 proposal 挂载标签，本卡中的“L0–L5 挂载”是适配说明，不是冻结 OS 的新层级。

## 5. 不采用的原文口径

以下内容保留在来源读本的“讲义主张”栏，不进入当前流程规则：

- “解决一个具体问题就能发一篇 Paper”（Luo PDF p.12）；
- “90% 顶会顶刊 / 10% 交叉领域”（p.23）；
- 每天“5–6 小时有效科研时间”（p.30）；
- 顶会顶刊“约 20% 接受率”（p.69）；
- “技术细节约三个创新点”（p.35）作为硬数量；
- p.57 “直接复制它文的内容”的字面做法；改为忠实转述、短引、页码和语义核对；
- 任何把“快速迭代”、拒稿鸡汤、venue 列表或政策链接变成用户人格、能力或研究价值判断的用法；
- SS 05 章“AI 能做就不人工做”的替代所有权口径；当前保持 M21 `REJECT`，用户先做核心定义、推理、代码和验收。

## 6. 何时可以升级为更强的采用

本卡目前可以直接作为个人读论文/小实验的适配入口；以下事项仍需单独证据或用户拍板：

1. 把 L0–L5 骨架写入冻结 OS；
2. 将整合卡公开、确定 CC BY-NC-SA 改编署名位置；
3. 把任何方法变成训练题面、评分 rubric 或自动 verdict；
4. 外部核验 PDF 中的论文/年份、政策链接、接受率、速度对比和截图细节；
5. 以此卡推断用户已经掌握某项能力，或据此对外联系导师。

## 7. 快速验收

这张卡被正确使用的最低证据是：

- 一份带页码和来源类型的 paper note；
- 一次用户先写 prediction 的最小实验；
- 一条 good/failure case 及经验证的原因；
- 一张用户自己重画或实例化的关键图/公式；
- 一次关掉答案后的变体或冷启动复述；
- 一行 claim ceiling 和贡献边界。

只有“看过 PDF、AI 生成了摘要、文件已写好”时，不算整合成功，也不更新能力等级。
