# EvoAgent Pattern Cards

These four cards extract only patterns demonstrated in the vertical slice. Every `Minimal interface` is a **conceptual extracted signature**, not a claim that an exact function with that name or signature already exists in EvoAgent. Static source shape is not runtime or production proof. All PM4Py and SBPN/SBTPN mappings below are `RESEARCH-HYPOTHESIS`.

## P-01 · Guarded state transitions
- **Problem:** A workflow's normal phases can be skipped or reordered unless phase changes are checked against an explicit transition relation; terminal persistence needs a separate prior-state contract.
- **Context:** In `ReviewHarness.run`, the normal phase path is `PENDING → PLANNING → EXECUTING → REVIEWING`, followed by direct terminal persistence for success, failure, or cancellation.
- **Forces:** Callers need simple progress updates; normal-phase jumps should be rejected; terminal writes and persistence races need their own safeguards; process state must not be mistaken for safety or risk state.
- **Minimal interface:** `transition(task_id: str, target: TaskState) -> None` — conceptual extracted signature, not an exact existing EvoAgent function.
- **Invariants:** **Demonstrated Harness invariant:** each normal phase edge sent through `ReviewHarness._transition` must belong to `ALLOWED` and a rejected normal-phase edge is not silently coerced. **Required store-level contract, not demonstrated:** direct terminal writes should validate or atomically condition on an allowed prior state.
- **Implementation in EvoAgent:** `evoagent/harness.py::ALLOWED`, `ReviewHarness.run`, and `ReviewHarness._transition` guard the PLANNING/EXECUTING/REVIEWING phase changes. Terminal outcomes are written directly through `evoagent/store.py::TaskStore.succeed`, `TaskStore.fail`, and `TaskStore.cancel`; those methods and `TaskStore.transition` do not expose an independent prior-state validation contract in the static reading.
- **What it does well:** Makes the Harness's normal phase order explicit and rejects an illegal normal-phase edge when it goes through `_transition`. It provides a partial conformance reference for later event-log analysis.
- **Failure modes:** A caller can bypass the Harness guard by using direct store methods, and terminal writes lack a demonstrated store-level prior-state check; therefore this card does not claim `PENDING → SUCCESS` is universally rejected. A process can also race if checking and persistence are not serialized across workers. Thread locks do not provide distributed serialization. Legal process order does not prove that findings are true, repairs are safe, or a risk state improved.
- **Alternatives:** Database compare-and-swap with a version column; transactional state-machine tables that validate all normal and terminal edges; event sourcing with optimistic concurrency; workflow engines that own transition durability.
- **Use when:** The workflow has a small explicit phase set and the Harness is the controlled entry point, while terminal/store-level gaps are separately guarded or accepted.
- **Do not use when:** Direct store writes are available to untrusted callers, all lifecycle edges must be enforced uniformly, or an in-process lock is being offered as distributed consistency.
- **PM4Py mapping:** `RESEARCH-HYPOTHESIS` — emit observed normal-phase and terminal writes as activities with `case_id`, timestamp, state before, and state after; compare Harness-routed edges with direct terminal writes and flag skipped or impossible traces. No PM4Py-compatible captured runtime log was produced.
- **SBPN/SBTPN mapping:** `RESEARCH-HYPOTHESIS` — represent process phases as places and both guarded and direct terminal writes as distinct transitions so the enforcement gap remains visible; do not rename process places as risk states without separately defined risk semantics. Probabilities, timing, and causal risk propagation remain `UNVERIFIED`.
- **Evidence:** `STATIC-CONFIRMED` from `evoagent/harness.py::ALLOWED`, `ReviewHarness.run`, and `ReviewHarness._transition`, plus `evoagent/store.py::TaskStore.transition`, `TaskStore.succeed`, `TaskStore.fail`, and `TaskStore.cancel`; source snapshot current working tree read 2026-08-10. Universal lifecycle-edge enforcement, runtime concurrency behavior, and production serialization are `UNVERIFIED` or absent from the demonstrated contract.

## P-02 · Checkpointed node execution
- **Problem:** Retrying an interrupted multi-node task can repeat completed work, but treating cached node output as full resume can hide lost in-flight state or duplicated external effects.
- **Context:** The Harness checkpoints node outputs and, on a later run, reuses outputs marked completed while reconstructing the input state.
- **Forces:** Recovery should avoid recomputation; retries must be bounded; external calls may have ambiguous outcomes; exact-once effects require durable identity and reconciliation beyond output caching.
- **Minimal interface:** `run_node(task_id: str, node: Node, operation_id: str) -> NodeResult` — conceptual extracted signature. The `operation_id` expresses a stronger desired idempotency contract and is not an exact current EvoAgent parameter.
- **Invariants:** **Demonstrated checkpoint invariant:** a node output found durably completed by `_completed` is reused rather than re-executed by the Harness. **Required for side-effect-safe retry, proposed and unimplemented here:** reuse one durable operation id across attempts, reconcile ambiguous outcomes before retry, and commit one logical result at most once.
- **Implementation in EvoAgent:** `evoagent/harness.py::ReviewHarness._run_node` performs bounded node retries; `ReviewHarness._completed` finds cached outputs; `ReviewHarness.resume` delegates to `run`, which rebuilds initial state and merges completed outputs. Current external reviewer invocation exposes no explicit operation id.
- **What it does well:** Reuses completed planning and other checkpointed outputs, bounds callback retries, and narrows the amount of work repeated after interruption.
- **Failure modes:** Checkpoints without arbitrary in-flight state restoration do not provide full durable resume. An external call may succeed before an ambiguous transport failure and then be repeated. A partial response or side effect may be duplicated because no explicit idempotency/reconciliation contract is visible.
- **Alternatives:** Durable workflow engines with replay semantics; transactional outbox/inbox; dependency-level idempotency keys; write-ahead operation records with reconciliation; deliberately at-least-once execution with deduplication.
- **Use when:** Nodes have durable outputs, replay from a known boundary is acceptable, and external effects are absent or independently idempotent.
- **Do not use when:** The requirement is restoration of arbitrary in-flight runtime state or exactly-once external effects without operation identity and reconciliation.
- **PM4Py mapping:** `RESEARCH-HYPOTHESIS` — record node start, retry, completion, and checkpoint reuse as separate activities under one case and correlation id; derive rework or retry-loop observations only after real timestamps and capture are available.
- **SBPN/SBTPN mapping:** `RESEARCH-HYPOTHESIS` — model pending, executing, completed, and ambiguous-outcome places with retry/reconcile transitions. Retry probabilities and delays cannot be assigned from the current static evidence.
- **Evidence:** `STATIC-CONFIRMED` from `evoagent/harness.py::ReviewHarness.run`, `ReviewHarness.resume`, `ReviewHarness._run_node`, and `ReviewHarness._completed`. `TEST-CONFIRMED` is bounded to `tests/test_production_features.py::test_failed_graph_resumes_after_last_completed_checkpoint`, registered as `EA-SLICE-001`: completed planning is skipped/reused, not full runtime-state restoration. External-call duplication is `UNVERIFIED`; the open narrower gap is recorded by `EA-SLICE-004`.

## P-03 · Evaluation gate engine
- **Problem:** A candidate can look improved on one measure while being unsafe, unevaluable, regressive on validation, or harmful on holdout data.
- **Context:** Prompt evolution evaluates seven conditions before activation: safety, validation readiness, holdout readiness, evaluation success, validation improvement, validation non-regression, and holdout non-regression.
- **Forces:** Missing datasets and unavailable providers must not become passes; improvement and non-regression are distinct; gate reasons must remain inspectable; domain transfer changes the meaning of each gate.
- **Minimal interface:** `evaluate(candidate: ArtifactVersion, datasets: EvaluationBundle) -> GateDecision` — conceptual extracted signature, not an exact existing EvoAgent function.
- **Invariants:** Activation occurs only when all seven evaluated conditions are true; `False` blocks activation; unknown or not-run gates do not count as passed; deferred, rejected, saved, and activated outcomes remain distinguishable.
- **Implementation in EvoAgent:** `evoagent/evolution.py::EvolutionEngine.propose` calculates and returns the decision, reason, metrics, seven gate values, version, and run id. Provider or dataset unavailability can defer evaluation rather than fabricate success.
- **What it does well:** Makes activation conjunctive and evidence-bearing, preserves non-regression checks beside improvement, and exposes individual gate values for diagnosis.
- **Failure modes:** Bad datasets, leakage, weak metrics, or correlated gates can still approve a poor candidate. Seven gate names do not transfer unchanged to SBPN experiments: each condition needs semantic redefinition and validation. A `None` gate can be misreported downstream if consumers collapse unknown into success prose.
- **Alternatives:** Sequential hypothesis testing; policy-as-code admission control; multi-objective Pareto review with hard safety constraints; human approval after machine evidence; formal contracts for selected properties.
- **Use when:** Candidate activation needs explicit, inspectable prerequisites and both improvement and non-regression evidence are available.
- **Do not use when:** The datasets are insufficient, the metrics do not represent the harm of interest, or stakeholders cannot define what every gate means.
- **PM4Py mapping:** `RESEARCH-HYPOTHESIS` — log dataset-ready, evaluation-completed, gate-result, and decision activities; check whether activation was preceded by all required gate events. Event order alone cannot establish metric validity.
- **SBPN/SBTPN mapping:** `RESEARCH-HYPOTHESIS` — gates may become enabling constraints on an activation transition, while candidate/evidence states become places. The seven EvoAgent gates must not be copied unchanged; safety semantics, stochastic parameters, and timing evidence remain `UNVERIFIED`.
- **Evidence:** `STATIC-CONFIRMED` from `evoagent/evolution.py::EvolutionEngine.propose`, source snapshot read 2026-08-10. No whole-chain runtime execution or `PRODUCTION-VALIDATED` activation outcome is claimed.

## P-04 · Canary/shadow intervention verification
- **Problem:** Activating a candidate globally before observing its effects can spread regressions; caller-supplied lane labels or a nonrepresentative sample can create false confidence.
- **Context:** A release manager assigns stable, canary, or shadow handling and offers methods to record candidate outcomes, roll back on a canary error budget, or promote after shadow observations; attribution from assignment to observation is not enforced by these methods.
- **Forces:** Exposure should be bounded; assignments should be reproducible; callers must preserve lane/deployment/task correlation; sample size and representativeness matter; zero exposure is a disabled protection state rather than safety evidence.
- **Minimal interface:** `observe(deployment_id: str, lane: Lane, outcome: Outcome) -> ReleaseDecision` — conceptual extracted signature with explicit attribution fields, not an exact existing EvoAgent function.
- **Invariants:** **Desired intervention contract, not enforced by current attribution APIs:** an observation should be bound to its prior assignment, deployment, task, and intended lane before it enters promotion/rollback accounting. **Demonstrated local rule:** `observe` excludes a supplied non-canary lane from canary accounting, but it trusts the caller's lane value/default; `observe_shadow` likewise trusts supplied data rather than proving prior shadow assignment.
- **Implementation in EvoAgent:** `evoagent/rollout.py::ReleaseManager.configure` sets policy and `assignment` selects a lane. `observe` trusts its `lane` argument (default `canary`) and writes through `evoagent/store.py::TaskStore.record_deployment_result`; it does not bind the observation to a prior assignment. `observe_shadow` writes through `TaskStore.record_shadow_observation` and does not enforce prior shadow/candidate attribution before counting or promotion logic.
- **What it does well:** Provides deterministic assignment, a bounded canary error-budget rollback calculation, and separate methods/data paths for ordinary deployment results and shadow observations. These are mechanisms, not proof of correct lane attribution or representative evidence.
- **Failure modes:** A caller can mislabel or omit lane context, the default canary label can admit an observation without a proven assignment, and shadow observations can lack enforced prior shadow attribution. Canary logic without representative sampling does not prove safety. A zero-percent canary yields no assigned canary evidence. Sparse observations, selection bias, delayed harms, or mismatched shadow traffic can invalidate promotion reasoning.
- **Alternatives:** Persist immutable assignment ids and require them on every observation; join observations to deployment/task records transactionally; offline replay; A/B testing with power analysis; staged ramps; feature flags with SLO monitors; human-controlled intervention trials.
- **Use when:** Callers can preserve verifiable assignment correlation, outcomes are observable quickly, exposure can be bounded, and rollback criteria are defined before release.
- **Do not use when:** Lane attribution is not trustworthy, harms are delayed or irreversible, the sample cannot represent production traffic, or zero exposure is being presented as validation.
- **PM4Py mapping:** `RESEARCH-HYPOTHESIS` — record assignment id, deployment/task correlation, claimed lane, outcome, rollback, and promotion events; check for outcomes without prior matching assignments and premature promotion. No captured rollout event log was analyzed.
- **SBPN/SBTPN mapping:** `RESEARCH-HYPOTHESIS` — model assignment-attributed stable/canary/shadow states and promotion/rollback interventions as transitions; rates, delays, contamination effects, attribution validity, and causal intervention semantics need controlled data and remain `UNVERIFIED`.
- **Evidence:** `STATIC-CONFIRMED` from `evoagent/rollout.py::ReleaseManager.configure`, `assignment`, `observe`, and `observe_shadow`, plus `evoagent/store.py::TaskStore.record_deployment_result` and `TaskStore.record_shadow_observation`. `TEST-CONFIRMED` is bounded to `tests/test_production_features.py::test_canary_assignment_and_error_budget_rollback`, registered as `EA-SLICE-003`: the tested configuration uses `canary_percent=100`, two outcome samples, and one rollback threshold. It does not test fractional or representative assignment, shadow promotion/attribution, zero-percent semantics, or production safety; those remain `UNVERIFIED`.
